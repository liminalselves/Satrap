# 任务恢复优化方案

状态: 请求存储、正常执行路径和列表查询优化已实施, 实测见 [优化结果](recovery-optimization-results.md). 历史版本号、异步存储调度和保留策略仍为后续设计

## 调查结论

此前基准见 [恢复验收记录](recovery-validation.md). 本次补查覆盖执行器、RunStore、上下文存储、检查点、归档恢复、Chat 服务及执行记录面板

| 问题 | 当前实现 | 影响 |
|---|---|---|
| 请求正文重复 | `engine.execute` 同时保存 `messages` 与 `asdict(prepared).messages` | 同一请求的消息正文占两份空间, asdict 还复制整份消息 |
| 多轮历史重复 | 每个模型步骤保存实际请求的完整历史 | 请求次数越多, 重复正文越多 |
| 大字段与状态同一行 | `agent_steps.input` 与 `status/result` 同行 | 更新小结果也操作包含大正文的记录, 增加存储维护成本 |
| 完成后重复读取 | 每次模型完成后再次 `store.step`, 为 usage 解码完整 input | 正常执行路径也承担恢复读取成本 |
| 重复权限查询 | `step/start_step/finish_step` 内部均调用 `get` | 一次三轮工具任务诊断中调用 get 44 次 |
| 全量一致性扫描 | 创建任务、每个模型/工具步骤、最终提交前后读取全部历史并哈希 | 开销随历史正文和步骤数量增长 |
| 列表 N+1 查询 | `list` 先查 ID, 再逐任务加载整行; summaries 再逐任务查询步骤 | 列表虽然不返回正文, 后端仍加载不需要的任务字段 |
| 异步路径阻塞 | 异步驱动中生成器直接执行同步 SQLite 和 JSON 工作 | 当前总耗时基准尚未测量事件循环停顿 |

隔离诊断采用与前次基准一致的 2000 条历史、三轮工具场景. 四份模型请求分别包含 2001 / 2004 / 2007 / 2010 条消息:

| 编码方式 | 请求 JSON 合计 |
|---|---:|
| 当前编码 | 25,176,748 bytes, 约 24.01 MiB |
| 每个请求仅保存一份 messages | 12,589,536 bytes, 约 12.01 MiB |
| 首份完整快照, 后续保存共享前缀引用与新增消息 | 3,152,205 bytes, 约 3.01 MiB |

后两项只在内存中对真实请求重新编码计算大小, 未实现持久化, 不能等同于数据库文件大小或延迟收益. 当前样本数据库包含约 6 MiB 空闲页, 说明还需要区分有效载荷、已分配空间和实际写入量

## 第一阶段: 请求存储与查询优化

这是建议先实施的范围, 保留当前历史指纹检查和副作用恢复规则

### 1. 分离正文与状态

增加内部请求编码模块 `execution/codec.py`, 同步和异步路径共用. 新记录使用格式版本 2:

- `agent_steps` 保留步骤身份、顺序、状态、恢复策略、结果等字段. 实施时复用原 `input` 列保存小型版本标记与 `_prepared` 元数据, 避免额外修改旧表结构; 旧记录仍从该列读取原始请求
- 新增 `agent_step_inputs`, 按 `(run_id, step_key)` 保存不可变的模型请求正文; 新步骤不在旧 input 列重复存正文
- `_prepared` 只保留 token 计数、策略、模型名等信息, 不再包含 messages; 不先 asdict 全量复制再删除, 而是明确选取元数据字段
- 请求参数与编码元数据分开, 解码后才形成模型调用参数, 防止版本号或引用字段误传给 SDK
- 模型调用开始前, 在同一事务保存请求正文与 running 步骤; 事务提交成功后才允许发起请求
- 完成时更新小记录, 正常路径直接复用内存中的 prepared 元数据; 恢复已完成步骤时也只读取结果与 usage 元数据

首次迁移使用新增表和兼容列, 避免启动时重写历史大表. 新表必须纳入归档、恢复和会话删除的作用域校验

### 2. 任务内请求增量

按实际准备后的请求编码, 不根据可变的 chat_history 或重新执行上下文压缩来重建:

```text
model:0  完整保存实际 messages
model:1  引用 model:0 的前 2001 条消息, 保存新增 3 条
model:2  引用 model:1 的前 2004 条消息, 保存新增 3 条
model:3  引用 model:2 的前 2007 条消息, 保存新增 3 条
```

共同前缀按完整消息结构比较, 包含多模态内容、tool_calls、tool_call_id 和 reasoning_content. 上下文截断、摘要或系统提示变化导致共享不足时, 回退完整快照; 选择编码后更小的形式

引用只允许指向同一任务内更早的模型请求. 限制链深, 例如每 8 次模型调用强制保存完整快照. 解码校验引用范围、前缀长度、版本和完整性摘要; 缺失或损坏时停止恢复, 不能重新猜测模型输入

这能消除单个任务内大部分重复历史. 不做跨任务或跨会话共享正文, 以控制清理、归档和 fork 的复杂度; 因而大量长历史任务仍需保留策略管理

### 3. 减少重复查询与事务

- 使用带作用域 JOIN / EXISTS 条件的步骤查询和写入, 合并身份校验与实际操作, 不靠删除校验提速
- 单次执行内缓存不可变任务参数, 可变状态仍在关键操作中校验
- 在执行作用域内复用连接, 每次事务仍保持短暂; 不跨模型或工具 I/O 持有事务
- 尝试将模型完成结果与对应 usage 状态放入同一事务, 消除独立 usage 提交; 需要抽出共用的 usage 数据准备逻辑
- 保留工具执行前保存意图、执行后保存结果的两个持久化边界; 不把整轮缓存在内存后统一落盘

当前三轮工具场景有 26 次 COMMIT. 本轮保留独立 usage 提交, 事务边界保持原语义; 上述合并 usage 方案未实施, 不计入本轮收益. 后续若合并四次 usage 写入, 理论上可减少到 22 次, 仍需独立验证

### 4. 摘要列表与分页

- 新增分页查询, 默认每页 20 条, 上限 100 条; 使用稳定的 `(created_at, id)` 游标和匹配索引
- 一次查当前页任务摘要, 一次批量查这些任务的步骤摘要, 不读取请求正文
- Chat 使用新分页接口, 返回 `next_cursor`; UI 增加加载更多, 按未完成状态筛选可单独查看旧任务
- 原有 Python `list_runs()` 的无参返回契约保留, 内部改为批量摘要查询; 不默默截断为第一页
- 如需查看单个步骤参数, 使用独立详情入口; 初始列表不带参数正文

## 第二阶段: 历史一致性版本

不能直接复用 `state_scopes.state_revision`: 它依赖检查点并会在回滚时恢复旧版本. 消息数量和最大 ID 也无法可靠覆盖原地修改

建议新增独立的 `history_generations(conversation_id, epoch, revision)`:

- 每次历史修改在同一事务更新 revision, 按事务/批次更新一次, 不逐消息更新
- 回滚也是一次新修改, revision 继续递增; 删除后重建使用新 epoch, 避免版本重用
- 普通消息保存、全量重写、检查点快照恢复、指针回滚、fork、归档恢复和任务最终提交都必须接入
- 元数据不是可随检查点回滚的消息状态; 归档恢复需要验证历史后建立新版本绑定, 不能盲目恢复旧版本号
- 每步比较小版本记录, 最终在 BEGIN IMMEDIATE 事务中再次校验并原子提交
- 创建任务、进程重启恢复和最终提交保留内容指纹校验, 以验证实际历史

这里有一个明确边界: 手写 SQL、旧版本进程或第三方绕过存储接口直接修改 chat_history, 不会递增应用维护的 revision. 仅保留首尾哈希无法保证在每个后续工具执行前发现这种修改

因此第一阶段继续使用完整指纹校验. 第二阶段只有在写入入口收口和兼容边界落实后才切换默认策略; 若仍要求检测任意外部 SQL 写入, 就保留当前严格扫描, 不能宣称版本号方案完全等价. 本方案不引入 SessionHandler Hook、执行期插件回调或数据库触发器

## 第三阶段: 异步响应与保留策略

异步优化应先测事件循环延迟再实施. 若 SQLite / JSON 工作仍造成明显停顿, 为异步驱动增加固定的存储 I/O 指令, 将阻塞工作提交到受限工作线程, 共享事务和编码逻辑. 这不是可注册的扩展点

工作线程中途取消不会自动停止数据库操作, 所以要明确等待在途事务收尾、最终状态写入和关闭次序. 不能简单对每个数据库方法套 to_thread 后立即宣布取消完成

保留策略先提供明确的手动清理与配置入口:

- 未完成或需要确认的任务不自动清理; failed / interrupted 仍可能恢复, 不能仅按时间删除
- completed / cancelled 可整任务清理, 不单独删除引用链中的步骤
- 已完成任务的显示回填仍依赖执行记录, 清理会失去该能力; 首版默认不自动清理, 设置中明确说明
- 大正文删除后优先允许 SQLite 复用页面; 文件压缩放到维护操作, 不在每轮结束时执行

## 兼容与验收

采用双读、新写 v2: 旧任务继续按原格式恢复, 不批量重写未知副作用任务; 不支持的未来格式明确报错. 新格式同样覆盖流式、多模态、usage 重建、Chat 回填、retry 和 fork, 公共工具定义与恢复操作语义不变

验收包括:

1. 新旧格式恢复后的模型消息与参数结构完全一致; 包括截断、摘要、图片、多个 tool call 和长引用链
2. 沿用现有真实进程终止测试, 并在请求正文/步骤意图提交前后、结果提交前后注入终止, 检查事务原子性
3. 覆盖所有历史写入入口、并发修改、回滚后回到相同内容、删除重建以及跨会话引用拒绝
4. 100 / 1000 / 10000 条任务的分页耗时、查询次数和内存, 验证成本受页大小约束
5. 重跑原 24 组基准, 分开报告有效载荷、SQLite 文件增长/空闲页、事务数、延迟、事件循环停顿; 补充默认上下文预算与截断场景

第一阶段以实测的约 3 MiB 请求编码量作为该固定场景的载荷目标, 不把它当成数据库文件或所有场景的体积保证. 优化后的毫秒数和物理写入量需实施后重新测量

建议实施顺序: 单条请求去重与正文分表 → 正常路径避免回读 → 任务内增量编码 → 列表批量查询和分页 → 版本校验与异步存储优化. 每步单独验证, 第一阶段即可获得存储收益, 无需等待版本号设计落地
