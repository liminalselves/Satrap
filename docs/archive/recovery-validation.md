## 实际进程中断与恢复

运行命令:

```powershell
python -m pytest tests/integration/test_chat_recovery_process.py --run-integration -q
```

使用临时数据目录、真实 `ChatHTTPServer` / `ChatService`、HTTP 鉴权、插件加载、SQLite 和文件锁. 模型使用离线测试替身, 通过精确屏障定位中断位置, 没有调用外部模型. 父进程强制终止子进程, 随后启动全新的后端进程, 通过公开 HTTP API 读取执行记录并继续原任务

任务包含两轮工具请求、三个工具步骤、三次正常模型请求. 分别在以下位置终止:

| 中断位置 | 续跑结果 |
|---|---|
| 第一个读取已完成, 写入发生后尚未保存结果 | 恢复后进入 `needs_attention`, 不执行任何模型或工具; 授权本身也不执行工具; 再次继续才重试写入 |
| 写入已完成, 第二个可重试读取尚未保存结果 | 自动重试该读取; 前面的读取、写入和模型结果全部复用 |
| 第二次模型请求已输出部分流式内容, 尚未完成 | 使用完全相同的保存消息重发该请求; 前面两个工具不重做; 最终回答不残留中断时的临时文本 |

三个场景均通过以下检查:

- 保持原任务 ID、原轮次和单个回复版本
- 再次回填完成任务不调用模型和工具
- retry 新建任务及回复版本, 工具按新任务重新执行
- fork 复制显示历史, 执行记录列表为空; 新会话不能恢复旧任务
- 子进程和日志句柄在测试结束时关闭, 不修改已有 Chat 数据

这是后端进程与 HTTP 接口验收, 不包含浏览器按钮操作或真实模型供应商的网络异常测试

验证结果: 全套默认测试 1348 passed / 19 skipped; 本文的三个进程测试另以 `--run-integration` 显式运行并全部通过. 默认跳过项包括外部服务集成测试、缺少 reportlab 的 PDF 测试和 Windows 符号链接权限测试. 本轮修改的源码及新增脚本通过 Pyright, 0 errors / 0 warnings

## 性能基准方法

```powershell
python tests/benchmark/benchmark_recovery.py --samples 7
```

原始结果保存在 `tests/benchmark/results/recovery.json`. 覆盖同步和异步、恢复关闭和开启、0 / 200 / 2000 条历史、0 / 3 轮工具调用, 共 24 组. 每组 7 个正式样本, 首次预热丢弃, 开关测试顺序交替; 每个样本使用独立数据库

每条历史约 512 汉字; 每轮调用两个返回固定文本的工具. 计时包括完整 `full_agent` 调用, 排除初始化与历史填充. 模型立即返回固定响应, 因而结果表示本机框架开销, 不是实际线上模型延迟. 同一场景下对模型请求消息计算摘要并比较, 同时校验请求次数、工具步骤数和最终历史行数一致

将上下文预算设为 400 万, 让长历史完整进入请求, 避免混入截断算法成本; 该值仅用于基准, 不代表真实模型支持的上下文长度. 默认 128k 预算下的超限截断应另行测试, 本次预跑中观察到它会显著拖慢长历史请求

SQLite trace 统计 INSERT / UPDATE / DELETE / COMMIT / SELECT 次数; 计时包含轻量计数开销. 存储指标为数据库文件净增长, 不等于 SSD 物理写入量, 也不包含日志文件与短暂 journal 写入

## 测量结果与下一步

环境为 Windows 11, Python 3.13.5, 本机临时目录数据库. 下表使用中位耗时, 单位 ms; 三轮工具场景均为 4 次模型请求、6 次工具执行

| 历史条数 | 工具轮数 | 同步关闭 | 同步开启 | 异步关闭 | 异步开启 | 数据库增长: 关闭 / 开启 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 12.7 | 51.8 | 20.7 | 59.4 | 0 / 20 KiB |
| 0 | 3 | 27.2 | 206.5 | 44.9 | 224.5 | 8 / 68 KiB |
| 200 | 0 | 21.8 | 95.3 | 31.4 | 109.8 | 0 / 1244 KiB |
| 200 | 3 | 62.3 | 371.0 | 84.8 | 413.6 | 8 / 3140 KiB |
| 2000 | 0 | 123.9 | 487.2 | 149.1 | 591.5 | 0 / 12308 KiB |
| 2000 | 3 | 429.1 | 1577.8 | 485.8 | 1737.2 | 8 / 30800 KiB |

数据库增长在这些样本中与同步 / 异步入口无关. 0 KiB 表示消息可使用已有页面空间, 不表示没有写入; SQLite 文件大小也包含已分配的空闲页. 原始 JSON 保留每个样本以及 P95, 7 次采样下 P95 实际等于最大样本, 不足以推断线上尾延迟

| 单次调用的 SQL 指标 | 无工具: 关闭 / 开启 | 三轮工具: 关闭 / 开启 |
|---|---:|---:|
| INSERT | 3 / 5 | 15 / 26 |
| UPDATE | 0 / 2 | 0 / 11 |
| COMMIT | 3 / 5 | 6 / 26 |
| SELECT | 0 / 16 | 0 / 76 |

初始化与历史加载已排除, 所以关闭恢复时可直接使用内存上下文, 计时区间没有 SELECT. 恢复增加了执行前重载、状态查询和一致性检查. 两种模式都没有按 token 写执行记录

本轮结论: 恢复行为通过验收, 长历史存储与耗时仍有明显优化空间. 建议下一轮优先处理:

1. 请求快照去重: 当前 `messages` 和 `_prepared.messages` 各保存一份相同正文, 多轮调用又重复保存完整历史; 先消除单条记录内的重复, 再评估任务级共享历史与消息增量
2. 一致性检查成本: 当前每个模型 / 工具步骤读取并计算完整历史指纹; 设计能覆盖追加、编辑、回滚的事务版本号, 在保留冲突检测的前提下减少扫描
3. 执行记录查询与保留策略: 列表当前逐个加载完整任务及步骤, 应改为摘要查询、分页并提供明确的保留规则; 本基准没有测量积累大量任务后的列表性能

以上是依据测量与代码审阅提出的优化方向, 本轮未修改存储格式、校验机制或现有入口的默认开关. 不应将离线倍率直接换算成真实供应商调用的整体倍率
