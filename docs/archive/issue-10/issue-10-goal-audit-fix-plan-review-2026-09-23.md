# Issue #10 修复计划复审

日期: 2026-09-23

对象: [修复计划](issue-10-goal-audit-fix-plan.md)

结论: 批次安排与覆盖 A1-A10 的方向可保留, 但当前计划不能原样作为关闭审计项的依据。以下意见针对拟议实现, 不表示这些修复已经执行。执行侧应先修订方案及验收条件, 再按批次实施。

## 必须修改的设计

### R1 / A3: 等待超时不能等同于子任务终态

计划的 `wait_for(shield(task), 5)` 超时后会继续进入 finally 摘除任务和锁登记, 而子任务仍可能在清理。下一轮因此可能建立新锁, 与上一轮清理并发, 原缺陷只是延后五秒发生。`shield` 保护内层任务免受外层取消传播, 不保证外层等待不会再次被取消; suppress CancelledError 后仍可能提前摘除。

修订要求:

- 任务与锁引用由子任务实际完成驱动清理, 不能由调用方退出驱动清理
- 调用方可以有界等待后退出, 但未终态任务须继续登记、占用容量, 同目标保持隔离或明确拒绝后续发送
- close 超时必须明确报告尚有清理未完成, 不得声称全部任务已终态
- 验收增加清理超过超时、外层重复取消、close 与取消竞争, 验证同目标不并发且任务不失踪

### R2 / A10: talk_value 的来源仍然错误

计划仍从 raw payload 提取 talk_value。此前确认回复已明确它是发言频率配置。当前 `wake_policy.evaluate_wake` 也没有计划所称的 frequency 分支; 频率判断位于 `WakeWindow.decide`。仅增加映射函数与带自造字段的事件测试, 无法证明正常配置下功能生效。

修订要求: 从平台、群和时段的有效配置取得 talk_value, 明确与显式阈值的优先级、单调映射及零值行为, 接入真实频率判断与试算。以不含 talk_value 的普通事件验证配置生效; 零值关闭自动参与不应连带关闭明确 @ 或手动唤醒。不增加群活跃度采集。

### R3 / A2: 不能把所有事件都当作当前真实消息进行追加

计划“当前消息必在 batch 内”不成立。`BackendManager.wake_platform` 在无 prompt 的待处理唤醒中, 已把整个 snapshot 拼成 event.message_str; 其手动 request_id 不等于各原始消息 ID。保留 projected 再追加 batch 会重复整段窗口。

`wake_timers.py` 还会保存一份消息正文, 在定时触发时重新读取 snapshot。原消息此时可能已消费或过期; 无条件保留旧 projected 会重新带入已经不属于实际 claim 的正文。

修订要求: 区分真实当前消息、独立手动 prompt、待处理窗口唤醒与定时唤醒。窗口类合成事件以实际成功 claim 的内容为准; 真实当前消息保留补全结果并按稳定身份去重。测试覆盖无 prompt 手动唤醒、部分 claim、过期/淘汰、定时前已消费和缺失原消息 ID。

### R4 / A1: 动作返回后才消费 flag 不足以防重放

两个并发请求能在首次动作返回前同时通过“未消费”检查。超时或断线还可能是远端已经处理、调用方未收到结果; 将 flag 保留为可用会允许再次执行。

修订要求: 校验和占用必须在首次网络等待前原子完成, 至少区分可用、执行中、已完成、结果未知。结果未知不得自动恢复可用。登记键及核验绑定适配器/账号、请求类别、flag、群号与 subtype; 好友请求不能复用群请求登记。可信账号身份验证应先于登记, 订阅过滤可以后于登记。重复入站事件不能重置已占用状态。

验收增加同 flag 并发、错误账号/请求类别、动作超时后重试、重复入站事件与断线重连。撤回回源后还应在实际执行前确认当前权限没有失效。

### R5 / A5: 持久化计划尚不能保证其声称的幂等和恢复语义

文件锁与原子替换解决文件写入完整性, 不自动解决“查重 → 占位 → 入队”的竞争。损坏后降级为空会遗失去重记录; 无条件淘汰最旧条目也可能淘汰 accepted/executing/unknown。仅把回执归为 sent/failed 会丢失混合发送的部分成功与未知结果。

修订要求:

- 明确 request_id 的作用域和请求指纹; 重用 ID 但参数不同返回冲突
- 在一个受保护事务中完成查重与持久占位, 成功落盘后才确认 accepted; 定义入队失败后的状态
- 在发送 I/O 前记录尝试, 保存各段结果或足以表达部分成功、未知结果的信息, 不将未知归为失败后自动重发
- 存储损坏时保留损坏文件并进入显式降级状态; 无法保证去重时拒绝依赖该保证的新请求, 可以继续启动其他功能
- 定义去重保留期限, 不因容量不足悄悄淘汰未决记录; 容量耗尽应明确拒绝或采用可恢复的归档机制
- 验收增加并发重复、落盘失败、入队失败、发送后未回写即崩溃、部分成功、记录损坏和容量耗尽

此外, 本节标题包含发送状态持久化, 但数据源主要是手动请求。须明确普通回复的已提交发送尝试如何纳入原方案要求, 不能仅完成手动查询就关闭全部持久化缺口。

### R6 / A7、A9: 新工具和文件发送须保持共同的发送约束

计划让新工具直接经过私有 `_send_forward`, 需要明确不得绕过 `send_message` 所在的整轮排序、容量和关闭生命周期。新增消息/转发读取工具同样必须核验实际对象归属, 不能只验证模型传入的 group_id。

文件上传 unsupported 后回落旧 file 段, 尚无目标实现支持该回落的证据。回落可以是经验证的兼容策略, 不能将“尝试了另一个动作”视为交付成功。上传动作的参数、URL 支持、成功响应是否含 message_id 及完成语义也必须按目标 SnowLuma 版本核对; 不能直接套用普通消息回执的假设。

修订要求: 统一经公共发送调度路径; 将上传/转发的调用结果也接入能力学习; 核对实际连接状态而非仅检查 bot 对象。重连时按实现版本/连接代次失效或重新确认能力缓存, 不假设实现始终不变。对未知兼容能力明确返回 unsupported/unknown 或使用已验证回落。补实际 SnowLuma 网络层与模拟 QQ 动作的混合链验收, 断言顺序及部分成功/未知结果, 不执行真实 QQ 管理动作。

## 必须补全的验收设计

### R7 / A4: 扣除媒体额度不等于裁剪顶层媒体

`remaining = max(0, limit - len(images) - len(videos))` 只阻止新增媒体, 不会删除已经存在的 100 张顶层图片。需明确顶层媒体也按同一额度裁剪, 再允许引用/转发消耗余量。

字符预算必须计入来源头、分隔符、截断提示及 A2 的窗口拼接, 在最终 UserCall 检查。配置允许极小限额时, 无法同时保证正文和来源标记完整, 应定义优先级及截断行为, 避免互相矛盾的测试契约。

### R8 / A8: 试算和记录的数据源覆盖不完整

当前 evaluate_wake 仅包含私聊、上游唤醒、直接提及、关键词与别名判断。只复用此函数不能试算 frequency/necessity、窗口、冷却及最长等待。应抽取与真实路径共用的决策逻辑, 用隔离的模拟窗口按样例时间推进, 不改生产窗口。缺少必要上下文时返回明确的无法判断原因。

A5 手动记录与 ProjectedInput.notes 无法覆盖普通未唤醒或提前限流的消息: 它们可能根本没进入投影。需要在实际决策/限流位置采集有界、可查询的逐次记录, 关联请求身份与发送结果, 再由 UI 展示。验收必须包含“没有执行投影也能查到拒绝原因”的案例。

脏状态保护除 Modal 关闭外, 还应覆盖页面内导航及浏览器离开, 或明确说明现有全局保护已覆盖并验证。

## 范围与交付口径

计划开头称两项证据不足问题由“用户裁定搁置”。本次可见对话和此前确认回复不能支持这一裁定; 如果裁定来自其他任务, 应补可追溯出处。否则保留为待验收事项, 不将讨论证据强度等同于豁免验收。

- 历史 ASR/LLM/SnowLuma 结果继续按原日期、版本和覆盖范围使用, 修改影响到的链路定向补验, 不要求全量重跑历史实验
- 发行/静态资源按 README 的源码安装、前端构建及实际 HTTP 托管验证, 不新增 exe 安装器要求
- 即使另有明确的延期决定, 也只能报告本批范围完成及剩余项, 不能把搁置项计为通过完整目标验收

pyright warning ≤1532 可以作为更严格的目标, 但若称为既有基线, 应给出对应提交和命令。各批次开始记录实际基线, 验收记录区分原有问题与新增问题。
