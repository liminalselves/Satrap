## 需要纠正或收窄的复审表述

### 1. talk_value 不是已证实的 NapCat 群活跃度数据

复审将它解释为“NapCat 系群活跃话痨值”, 并推导必须有群活跃度输入, 该解释没有当前方案或参考项目证据支持。[MaiBot 官方配置文档](https://docs.mai-mai.org/manual/configuration/bot-config#什么时候发言) 将 talk_value 定义为群聊发言频率配置, 提供按聊天/时段设置频率的规则。原方案要求“talk_value 映射为阈值”, 不是新增 NapCat 数据查询。

映射缺失成立, 但修复不应因此扩大成群活跃度采集。具体函数属于实现设计: 保持值增大时参与更积极的单调语义, 明确边界与显式阈值优先级, 有可解释的前端配置和试算即可; 不从参考文档推断 Satrap 必须采用完全相同的取值算法。

### 2. File 缺失不等于已验证协议失败

接受“分流确认缺失”; 但“file 段大概率不产生文件”和“先 upload 取 file_id”不能直接作为已经核实的目标版本结论。需要对 SnowLuma 1.14.17 的实际动作实现核对参数、返回和完成语义, 不能只查字符串零命中或依据通用 OneBot 假定失败。测试继续遵守既定范围: 实际 SnowLuma 网络层, QQ 动作可模拟, 不增加 QQ 登录要求。

### 3. 历史记录无需交给用户一律重新裁定

原审计没有否定历史记录, 也没有要求“本轮必须重新调用 API”。保留历史结果的已验证范围, 结合版本差异判断是否重验, 是正常工程验收职责。文字记录存在与独立重现是不同证据强度, 两者应标明, 无须为了接受一份历史记录额外请求用户授权。

2026-09-22 合成正弦返回空文本, 只能证明服务接受格式及路径执行, 不能证明语义转录准确; 2026-09-21 TTS 中文文本链路的覆盖范围另行保留。A2 修复涉及最终模型入参, 至少需要对应组合路径的定向回归。

此外 `probe_snowluma.py` 使用运行时随机 token, 不从 `.toolkit` 读取固定凭据; 复审所写该脚本的凭据来源需更正。真实 ASR/LLM 历史调用的 `.toolkit` 来源不受此更正影响。

### 4. 发行门槛以可复现的实际分发形态为准

复审“没有安装器”的事实不等于没有 Python 包构建配置: setup.py 与 pyproject.toml 已构成 setuptools 构建入口。原方案要求实际打包/静态服务版本正确, 并未要求 exe/安装器; 原审计“安装后的静态服务”措辞过窄, 已收窄。

README 当前明确的是源码目录内 `pip install -e .`、`npm run build` 后启动服务。可以直接在干净检出验证该链路, 检查 index 引用的资源哈希、HTTP 返回资源和 ASR/平台配置页面, 并确认 SnowLuma/临时凭据未被纳入交付。若宣称 wheel/sdist 独立安装也提供 UI, 则应另外检查该产物是否包含/定位静态资源; `include_package_data=True` 本身不能证明包内有 dist。无需将这一区别转成用户必须回答的产品问题。

### 5. 测试数量差异不能确定归因于环境

`1862 + 19 = 1881`, `1875 + 7 = 1882`, 总数也差 1。仅凭当前摘要无法断定差异全部来自跳过项变化, 也无法据此判定代码回退。准确表述应为“两个历史输出分别保留, 差异原因未完成逐 nodeid 核对”; 如需解释, 比较当时提交、pytest 命令、收集列表与环境。当前报告以实际执行的 1875 passed / 7 skipped 为准。
