# Issue #10 整体方案对照审查

审查日期: 2026-09-20  
方案同步完成: 2026-09-21  
Satrap 基线: `1ecb13c`  
被审查文档: [实施方案](issue-10-plan.md)

## 结论

现有方案已覆盖议题所需的主要功能, 但距离稳定交付仍有执行隔离、配置生效、身份传递和可诊断性方面的不足。补齐页面和 API 数量不足以解决这些问题。此次列出 10 项, 前 5 项应先于扩展群聊规则和管理工具开放完成设计与行为测试, 后 5 项随对应功能交付。

这里对比的是读取过的固定源码快照, 不是对 AstrBot / MaiBot 进行完整运行评测, 也不假定两者在所有方面都优于 Satrap。部分修正是根据 Satrap 本地调用链推导出的要求, 并非声称参考项目已经实现了同样方案。

## 必须优先处理

### R1. 高: 同平台串行分发会放大慢请求影响

本地依据: `satrap/core/platform/__init__.py:101` 使用无界入站队列, `:697` 的每适配器工作器逐条等待 `_process_event` 完成。现有方案只明确了出站队列, 未解决入站排队。一个群的 ASR、引用回源或 LLM 长时间等待, 可以阻塞同一适配器的其他群, 心跳/状态事件若沿同一路径接入也会被延迟。

对照: [AstrBot EventBus](https://github.com/AstrBotDevs/AstrBot/blob/6914bc3aa61e14ca9a9c2cb37a0f9ec1ff5d6334/astrbot/core/event_bus.py#L39) 将管线执行派发为任务并持有引用。借鉴接收与执行解耦, 不直接复制无显式并发上限的派发方式。

修正: 适配器接收与轻量校验保持有序, 慢执行按最终会话键串行、不同会话有界并发; 重用 SessionManager 的现有执行约束, 避免叠加锁死。入站、等待执行和出站均有容量/TTL/满载策略。状态更新与回包不能等待 LLM 完成。任务受后端生命周期管理, 停止和重连时处理未完成状态。

验收: 同平台群 A 的模型请求挂起时, 群 B 及心跳仍可处理; 同一最终 Session 不并发执行; 洪峰不造成无界任务增长; 队列满时有可观测结果。

### R2. 高: 限流与唤醒顺序造成无关群消息消耗额度

本地依据: `scheduler.py:105` 附近先调用 RateLimiter.check 并可能发送反馈, `:120` 才检查唤醒。RateLimiter.check 会实际扣除令牌, 不是无副作用查询。

本次离线探针使用真实 OneBotAdapter、PipelineScheduler 和 RateLimiter, 将模型与发送客户端替换为 AsyncMock。设置 burst=1、rate=0.01 后提交两条不含唤醒词和 At 的普通群消息:

```text
ordinary_group_messages=2, session_calls=0, outbound_feedback=1
```

这确认即使机器人不应参与对话, 普通聊天也可能引发“请求频率过高”反馈。接入群消息积压计数后, 沿用该顺序还会提前丢掉待观察消息。

修正: 分开接收防洪、外部补全预算和模型调用限流。接收防洪默认静默; 普通观察消息不扣模型令牌; 唤醒候选才申请执行额度, 引用身份查询使用独立小预算。自动参与被限流不向群刷反馈, 显式请求的反馈按策略节流。

验收: 大量普通消息不耗尽 @机器人的执行额度, 无唤醒消息不产生反馈; 接收防洪仍能限制无效洪峰; 引用查询不能绕过回源预算。

### R3. 高: 群级唤醒与用户级上下文路由没有明确契约

本地依据: `UserManager.py:804` 的 resolve_session 按 user_id、platform、session_type、provider 查找上下文, 当前 scheduler 未把 group_id 作为独立上下文维度传入。相同用户在不同群可能路由到同一会话。原方案同时写了“按群累计消息”和“不合并用户私有会话”, 却未明确统计窗口、上下文、权限主体和回复目标分别是什么。

对照: [AstrBot 平台编辑器](https://github.com/AstrBotDevs/AstrBot/blob/6914bc3aa61e14ca9a9c2cb37a0f9ec1ff5d6334/dashboard/src/components/platform/PlatformEditor.vue) 提供会话配置绑定; [MaiBot 触发输入](https://github.com/Mai-with-u/MaiBot/blob/fb4a8bd917d6fe373df9e3c22289d229e7f1b344/src/maisaka/reply_necessity.py#L26) 依赖明确定义的当前聊天快照。不能只复制触发算法而省略其上下文边界。

修正: 明确区分平台聊天标识、最终 Session 标识、触发窗口标识和当前操作者。支持显式 context_scope: legacy_user、group_member、group; 既有配置保持原映射, 新建 OneBot 配置推荐 group_member, 群共享上下文必须显式选择。群级活跃度可以用于决策, 但投影输入必须遵守最终上下文范围; 用户隔离模式不把其他成员窗口内容自动注入该用户上下文。切换 scope 创建新映射并保留旧会话, 不静默合并历史。UI 显示生效范围和变更影响。

验收: 同用户跨群、同群多用户、群共享、私聊及手动唤醒均有明确且一致的 Session/回复路由, 权限不会继承其他用户。

### R4. 高: 管理工具尚缺可信的逐次调用上下文

本地依据: `satrap/core/type.py:250` 的 UserCall 仅携带会话选择、文本和图片/视频, 没有平台来源、调用者、群或消息 ID。scheduler._check_permission 默认返回 True。原方案说“核验调用者权限”, 但未说明身份如何穿过 Session 到达工具, 也未说明 SessionClassProvider 和 EdictumProvider 如何分别接入。

修正: 在边界产生不可由模型参数覆盖的类型化调用上下文, 贯穿 UserCall、会话执行和工具调用, 包含 adapter_id、self_id、origin_chat、actor、source_message_id、request_id。人工唤醒使用已认证主体, 群共享调用也保留本轮真实主体。群管理工具基于这份上下文与用户配置校验目标, 不接受模型自报管理员身份。分别定义两种 Provider 的注入/注册路径; 不具备接入能力的会话类型返回明确不可用。工具是否启用仍完全由用户配置, 不新增固定逐次审批。

验收: 共享会话中管理员发言后, 普通成员不会沿用其权限; 并发请求不串上下文; 已启用但目标适配器不支持的工具清楚显示原因; 两种 Provider 的支持范围可验证。

### R5. 高: 平台配置保存与运行时生效目前脱节

本地依据: `satrap-ui/src/pages/Platforms/index.tsx` 保存后调用 reloadConfig 并提示平台已热加载; `BackendManager.py:423` 的 reload_config 仅重载模型、会话类和 Edictum, 没有协调平台适配器配置。原方案提出分别反馈保存/生效, 但没有落实后端应用过程。

修正: 返回 saved_revision、active_revision、applied/pending_restart/failed。唤醒、回复、媒体策略以不可变配置快照在新请求生效; 监听端口、鉴权等连接字段需要针对适配器协调重连/重启。先校验候选配置, 应用失败时保留旧生效值并返回失败原因, 不以通用 reload 成功代替适配器更新成功。删除/停用实例要关闭工作器和计时任务。UI 显示尚未生效的变更与受影响实例。

验收: 保存端口、token、唤醒词后分别验证实际行为; 重连失败页面不能显示全部生效; 运行中的请求绑定旧快照, 后续请求绑定新快照。

## 随对应批次补齐

### R6. 中: 去重和重启恢复只覆盖了局部

对照: [MaiBot 入站去重器](https://github.com/Mai-with-u/MaiBot/blob/fb4a8bd917d6fe373df9e3c22289d229e7f1b344/src/platform_io/dedupe.py) 对普通外部消息使用有界 TTL 缓存。原方案主要说明通知去重和手动 request_id, 未明确普通消息重复、机器人回声、进程重启和发送结果不明时的状态。

修正: 普通消息也按实例、账号、聊天和平台消息 ID 去重, 排除机器人自身回声进入唤醒规则; 缺失 ID 的事件不能仅按文本永久去重。待观察窗口允许进程重启后清空, 但已接受的人工请求和已提交发送尝试用现有状态存储留下最小记录。重启后结果不明的发送标记 unknown, 不自动重发。新发送回执优先在 OneBot 落地, 对其他适配器的旧式 None 返回保留兼容层, 不一刀切认定失败。

验收: 同一入站重复不重复调用模型; 同样文字的两条不同消息不误合并; 自身回声不触发回复循环; 部分发送后断线/重启不会重发全文。

### R7. 中: 前端表单缺少完整的配置编辑与诊断能力

对照: [MaiBot useConfigForm](https://github.com/Mai-with-u/MaiBot/blob/fb4a8bd917d6fe373df9e3c22289d229e7f1b344/dashboard/src/hooks/useConfigForm.ts) 分离配置/schema 加载、草稿和修改检测; [模型配置 hook](https://github.com/Mai-with-u/MaiBot/blob/fb4a8bd917d6fe373df9e3c22289d229e7f1b344/dashboard/src/routes/config/model/hooks/useModelConfig.ts) 有配置副本与保存协调; [AstrBot 平台编辑器](https://github.com/AstrBotDevs/AstrBot/blob/6914bc3aa61e14ca9a9c2cb37a0f9ec1ff5d6334/dashboard/src/components/platform/PlatformEditor.vue) 使用配置元数据、变更快照及保存条件。

修正: 新增字段由后端校验定义导出描述与默认值, 前端复用现有表单组件, 复杂群/时段列表用专用编辑器。补草稿脏状态、离开提醒、恢复默认/恢复继承、字段级错误和有效配置预览。使用配置修订号检测 UI/CLI 同时编辑, 防止后保存覆盖前修改; 不为本议题重建全部设置页或照搬整套多版本 UI。提供不调用模型、不写入窗口的唤醒规则试算, 返回命中/拒绝原因、配置来源、阈值和可选下一次检查时间。

验收: 后到的 schema 或刷新不覆盖未保存编辑; 旧修订保存返回冲突; 规则试算与真实路径使用同一策略函数; 暗色/浅色、窄屏及键盘操作可用。

### R8. 中: 运行状态缺少来源和失效规则

对照: [MaiBot-Napcat 心跳监视器](https://github.com/Mai-with-u/MaiBot-Napcat-Adapter/blob/5f2e9f266f3c6812054d0c9c716bc35c184004dd/heartbeat_monitor.py) 维护超时状态; [禁言跟踪器](https://github.com/Mai-with-u/MaiBot-Napcat-Adapter/blob/5f2e9f266f3c6812054d0c9c716bc35c184004dd/services/ban_tracker.py) 根据通知维护禁言并校正状态。Satrap 方案已有状态展示, 但未规定依据和过期行为。

修正: 区分进程启动、OneBot 连接、身份确认、可发送状态。维护最后事件/心跳/动作回包时间、最近错误和状态更新时间, 缺失心跳且仍有正常 I/O 时不能直接判定离线。机器人被禁言、踢出或账号改变时使能力/身份缓存失效, 调用前与发送前再次判断可用性。首期每个适配器实例绑定一个 self_id, 拒绝第二账号悄悄覆盖共享 bot_self_id。以 request_id 关联唤醒、补全、模型和发送状态, 提供有界、脱敏的最近处理记录及刷新恢复接口。

验收: 页面能解释“未唤醒”“已接受”“被限流”“转录失败”“发送未知”等不同结果; 断线恢复后状态能校正; 模拟 QQ 离线不使实际 OneBot 通信验收误判失败。

### R9. 中: 完整工具范围与实现差异仍需要可执行矩阵

方案列出完整工具是必要的, 但不能用 SDK 动态属性存在与否判断 SnowLuma 支持。设置管理员、匿名操作等协议动作可能受实现和平台权限限制。

修正: 为每个动作登记标准/扩展归属、参数、响应、工具名、权限范围、是否只读、是否可安全重试及能力状态。能力状态区分未知、支持、不支持和暂不可用; 不用执行踢人、审批等写动作探测支持。完整封装和可配置工具保留, 对不支持能力返回类型化原因, 前端解释不可用条件。工具开关与实例能力共同决定模型可见性, 配置关闭不能仍保留旧工具注册。

验收: 全清单均有契约测试, 标明 SnowLuma 实际网络验证与 QQ 侧模拟的边界; 无法证明真实 QQ 执行的项不标成真实执行通过。

### R10. 中: 内容预算和附件生命周期需要跨阶段定义

原方案已有文件大小、递归深度、临时文件清理和上下文冻结, 但缺少跨文本/引用/转发/ASR 的合计输入预算以及排队时的资产归属。同步完成事件 finally 清理不能直接套用到延迟触发任务。

修正: 区分组件摘要、用户当前正文、引用资料与平台身份, 按一次请求的字符/token/媒体总预算投影。超限优先保留当前问题和来源信息, 对删减位置给出标记, 避免只按单文件上限累计出超大输入。待处理窗口只存元信息, 真正触发后获取媒体; 任务接管的临时资产归任务清理, 超时/取消/异常均覆盖。ASR 成功但空文本、部分媒体失败和文件 URL 过期分别可观察。真实 ASR 用可核验短音频验证关键文本进入最终 UserCall, 不以 HTTP 200 作为全部验收。

验收: 多附件/嵌套转发总预算不超限, 取消后不泄漏临时文件, 队列等待不会引用已被其他事件清理的资产, 文本和媒体保持可解释的来源对应。

## 不建议照搬的部分

- 不引入 MaiBot 的完整 Planner、注意力切换和持续自主聊天运行时; 本次采用确定的可选唤醒规则和现有 Session 执行模型
- 不复制 AstrBot 每条事件直接创建任务的方式而忽略总并发、容量和同会话顺序
- 不新建完整聊天客户端、独立群管理工作台、提供商市场或复杂配置版本中心; 复用 Satrap 已有页面、状态存储和配置服务
- 不增加本地 ASR 推理框架适配; 继续使用用户已裁定的 OpenAI 兼容 API, SnowLuma 不随 release 分发
- 不把其他项目的缺省触发频率、超时和发送长度直接当作 Satrap 或 SnowLuma 的正确参数

## 三项补充意见复核 (2026-09-21)

1. **[中] P0a 过载: 成立。** 原批次横跨调度、会话映射、两种 Provider、配置应用和 UI, 验收失败难以归因。主方案现拆为 P0a-1 执行基础与隔离、P0a-2 配置应用闭环、P0a-3 可信调用身份。前两项不互为交付前置, 分别用启动配置和现有连接字段验收; 身份契约用测试工具独立验证, 再补共享范围集成测试。明确 P0b/P2 的功能依赖, 不再要求三个子批次一起交付。
2. **[低] AstrBot 出处不精确: 成立, 但应区分配置读取与实际行为。** 固定提交的 respond/stage.py 第 57-62 行确实读取引用/提及配置, 不能据此证明执行了装饰。实际 [At/Reply 插入](https://github.com/AstrBotDevs/AstrBot/blob/6914bc3aa61e14ca9a9c2cb37a0f9ec1ff5d6334/astrbot/core/pipeline/result_decorate/stage.py#L431) 在 result_decorate 第 431-445 行, [文本分段](https://github.com/AstrBotDevs/AstrBot/blob/6914bc3aa61e14ca9a9c2cb37a0f9ec1ff5d6334/astrbot/core/pipeline/result_decorate/stage.py#L209) 也在该模块。主方案改为两个实际行为链接, 不改变原设计结论。
3. **[低] 群白名单未覆盖: 成立, 作为补充配置采纳。** 当前 OneBot adapter 只有 enable_group 总开关, 原方案的群级唤醒覆盖不等价于统一群范围限制。新增实例级 group_whitelist, 缺省/空列表不限制群范围, 非空仅允许列出的群, 仍服从群聊总开关和其他权限。过滤早于观察/回源, 手动唤醒、群工具和主动发送不能绕过; 技术状态和动作回包继续处理。同步补前端、热更新边界及验收。字段本身成本低, 但完整交付不能省略入口一致性、ID 校验及配置收紧后的待处理清理。

本次核对了当前两份方案、OneBot 群消息入口和 AstrBot 固定提交原始文件, 并按原始文件行号校正链接。上述为方案修正, 未声称白名单或批次对应代码已实现。
