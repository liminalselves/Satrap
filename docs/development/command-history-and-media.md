# 命令历史与媒体输入

## 命令写入上下文

内置 SimpleSession 和 AsyncSimpleSession 接受会话参数:

```yaml
command_history_enabled: false   # 是否将已执行命令及其回复写入模型上下文
```

- 默认关闭, 不影响命令执行与 Chat 展示
- 开启后保存 user 命令和 assistant 文字结果, 不额外调用模型
- 无返回内容时只保存命令; 内部执行异常不伪造成功记录
- CommandAction 不自动进入源会话或目标会话
- 清空, 恢复或编辑历史后, 本轮命令不再追加, 防止历史回灌
- 未识别或已禁用命令仍沿用普通消息处理规则
- 开关只影响之后执行的命令, 不清洗或补写已有历史

Chat 设置支持草稿预选与已有会话修改, 使用 session.commands 覆盖域保存,
重建运行时和分支时沿用, 不依赖插件生命周期
平台在 Edictum 命名会话参数中配置同名字段

命令执行和历史写入受会话运行锁保护
分支区分明确保存的空上下文增量与旧数据的未知增量,
不会把未记录的命令轮次当成旧数据, 再从后来的对话推断上下文

## 模型媒体能力

```yaml
supports_visual_input: true         # 是否支持图片输入
supports_native_video_input: false  # 所接 API 是否支持当前 video_url 格式
video_frame_interval: 2.0           # 动画和兼容视频的采样间隔秒数, 范围 0.5 至 5.0
```

新字段缺省为 false, 不根据模型名称或旧视觉开关猜测原生视频支持
旧 supports_visual_input 配置继续表示图片能力, 视频在没有原生声明时走抽帧兼容
共享模型编辑框提供两个能力开关, 兼容模式下提供间隔滑块和数值输入

实际视频的处理顺序:

1. 原生视频声明开启: 直接传视频, 不同时附抽帧图片
2. 原生声明关闭且图片能力开启: 根据间隔抽帧
3. 两种能力均未开启: 新输入明确拒绝, 旧历史仅保留文字占位

原生请求失败时报告错误, 不自动发起第二次抽帧请求
原生模式不提供剪辑功能, 显式时间区间不能被悄悄忽略
兼容模式只处理画面, 明确注明未处理音轨

## 平台分类与实际格式

OneBot 按 image/video 消息段映射, Misskey 按附件 MIME 映射,
适配器保留原分类及来源, 不把全部 GIF 强制改成 Video 组件

新输入在固定媒体时检查实际内容:

- 真正 GIF, 动画 WebP, APNG: 使用 Pillow 确认动画, 按时间采样
- 实际 MP4/MOV/WebM/MKV/AVI: 按视频能力路由, 即使原平台标签是图片
- 静态图片: 沿用静态路径
- 既有远程静态图片历史保留旧 URL 语义, 不在每轮重复下载

Misskey 继续读取附件 url, 不将 thumbnailUrl 当成原动画
OneBot 的图片回源仍由适配器完成, 通用媒体层不越过平台下载策略

## 采样与分段

采样从指定区间起点开始, 按秒而不是固定帧数选取, 并补充末尾有效画面
使用真实时间戳, 去掉重复选择的同一帧, 每帧带媒体标识与时间说明
GIF 由解码器处理透明度, 叠帧与帧清除; 透明背景合成白色后编码 JPEG

单轮限制:

| 项目 | 值 |
| --- | --- |
| 原媒体单项及新输入总量 | 32 MiB |
| 请求图片数 | 16 张 |
| 请求媒体总量 | 32 MiB 原始字节量对应的编码预算 |
| 采样图片最长边 | 1600 像素 |
| 单次采样图片文件总量 | 24 MiB |
| 解码帧数 | 6000 |
| 累计解码像素量 | 20 亿 |
| 单帧像素量 | 4000 万 |
| 解码超时 | 30 秒 |

没有固定的单视频 8 帧上限
完整区间超过预算时返回 media_id 和分段提示, 不擅自增大间隔或只取开头
同一密度下的超限判断也缓存, 后续轮次不反复启动解码器

base_take 提供:

- read_document(path, ..., start_time=0, end_time=None): 已授权本地图片, 动画, 视频和文档
- read_media(media_id, start_time=0, end_time=None): 当前会话已收到或读取的媒体

read_media 不接受任意文件路径或网络地址, 只能读取当前工作流已登记的 ID
连续分段前应先记录已看区间的文字观察
请求预算优先保留最新完整媒体组, 旧画面改为明确的本轮缺省占位,
原始历史和媒体引用保持完整; 本轮全新媒体组本身超限时明确失败
预算计算在抽帧展开后进行, API 边界另做最终数量和字节检查

## 性能与存储

视频依赖通过 python -m pip install -e ".[video]" 安装, 使用当前解释器的 PyAV,
不依赖系统 ffmpeg 命令, 缺失依赖时明确提示

解码进程使用 sys.executable -I -B -X utf8 启动,
Windows 隐藏窗口, 同时最多两个解码进程, 每个视频解码器使用一个线程
父进程在取消和超时后终止并回收子进程
视频只接受已固定的本地容器, 显式限定容器格式和 file/pipe 协议,
不把输入当作播放列表, 不让解码器自行联网或读取外部文件

按实际时间跳转和连续解码, 不为每帧重开文件,
只对选中画面及末尾画面进行图像转换, 缩放和编码

实际数据库旁的 media/<数据库路径摘要>/ 下保存:

- blobs: 内容摘要去重的媒体字节
- references: 工作流持有权, 数据库和会话分别隔离
- frames: 依据内容, 区间, 间隔和尺寸生成的可重建采样缓存

缓存上限为 256 MiB, 按最近使用时间和 24 小时闲置时间清理,
完整结果原子发布, 当前读取与淘汰互斥, 同内容任务复用结果
锁文件按固定桶分配, 避免每个区间永久积累一个锁文件

Chat 媒体上传及预览限制同步为 32 MiB, 普通文档上传仍为 10 MiB,
上传路由为 Base64 编码后的请求体预留空间
动画和视频的宿主上传路径使用原媒体硬链接别名, 不再额外保存一份相同字节;
归档和恢复同样优先硬链接, 跨卷或文件系统不支持时回退复制

历史中的动画和视频保存引用, 发送请求时才读取和编码
任务恢复记录中的图片及视频同样改为去重引用, 不在每轮 JSON 重复保存 Base64
已被恢复记录引用的画面保持会话持有权, 不因采样缓存淘汰而丢失

分支只复制截止轮次实际引用的媒体持有权, 不带入之后轮次的媒体
归档包含媒体清单和去重原文件, 不归档可重建缓存
删除或归档会话时释放持有权, 只有无人引用的字节才回收
恢复归档时先恢复媒体, 再发布数据库记录
既有 Data URL 历史继续兼容; 已经只存第一帧的旧记录不能恢复动画
