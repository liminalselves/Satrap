## 1. 群聊全触发模式

现有 wake_mode 仅包含 explicit, frequency, necessity, 没有独立的全触发形式

新增 wake_mode=all, 前端显示为 "每条消息触发"

### 行为契约

- 群聊中每条通过平台准入且可用于模型输入的正常用户消息都满足唤醒条件, 无需 @, 唤醒词, 消息数量阈值或必要性评分
- 文本, 图片以及已支持且已启用处理的语音, 文件, 引用和合并转发纳入输入能力核验, 不把全触发实现为仅统计文本消息
- 本模式不使用自动参与冷却, 消息数量阈值, 必要性阈值及最长等待设置; 前端注明这些参数在此模式下不生效
- 保留平台启用状态, 群准入名单, 发言者身份核验, 去重, 会话互斥, 限流和队列上限; 被拒绝的消息返回明确诊断原因
- 自身消息, 出站消息, 通知和请求事件不因全触发额外唤醒模型; 已被命令系统消费的消息沿用命令处理流程
- "每条消息触发" 表示每条合格入站消息进入正常处理判断, 不承诺超载时每条消息都单独调用模型或必然产生回复; 合并处理仍注明来源, 不静默丢失身份
- 工具授权始终来自宿主保存的真实请求者; 群上下文中的其他成员, 历史管理员消息或 @ 对象不改变当前调用者权限
- 共享唤醒层实现该模式, 不在具体平台适配器中写死; 支持平台默认, 群覆盖及时段规则, 沿用既有覆盖优先级
- 默认仍为 explicit, 旧配置不自动启用 all; 私聊行为保持现有契约

### 唤醒落点与窗口消费

- 在 satrap/core/pipeline/wake_policy.py 的 evaluate_wake 添加群聊 all 分支, 返回 triggered=True, rule=all; 执行前仍经过 scheduler 的来源, 权限和绑定检查, 执行后仍经过输入可处理性和限流检查
- all 不加入 scheduler.automatic_eligible, WakeWindow.decide 和 WakeTimers.schedule 的 frequency/necessity 集合; 本模式不调用自动参与 decide, 不用 automatic=True 重新核对阈值, 不创建最长等待计时器或冷却重排
- 保留 scheduler 现有 observe/claim 分离: 普通非命令群消息仍通过 WakeWindow.observe 保留轻量来源快照; 唤醒由 evaluate_wake 决定, 等待会话锁后以 claim(..., automatic=False) 原子消费候选快照
- 窗口投影复用 input_projection.py 的 sender_label 与 select_window_media, 保留每条 actor_id, message_id, 昵称和文本/图片位置; 当前事件的正文和附件单独走现有投影, 不重复插入本事件的窗口副本
- 不以 automatic=False 意味着免去提交前复核: 在会话锁内重新核验有效 all 模式, 平台准入, 会话绑定及路由代次; 排队期间切换模式或撤权, 旧请求不能沿用旧 all 判断执行
- 已被其它有效提交消费的消息不能由竞争事件再提交; 实现时区分当前消息已认领与原本不能入窗的媒体事件, 不能仅凭 batch 为空丢弃合法语音, 文件, 视频, 引用或转发
- observe 现状只保留文本/图片引用, 不承诺将所有组件跨事件合并; 其它受支持组件由其原事件继续处理, 不得把仅有文本/图片的窗口快照当成完整原事件并提前丢弃其它组件
- 合并不改变 UserCall.origin, 授权仍只取当前真实请求者; 窗口内其它成员的来源标签是正文证据, 不能作为当前调用身份或管理员授权
- 不新增刻意等待的 all 聚合计时器; 只复用已有尚未消费的窗口消息, 超载仍沿用有界队列和限流诊断; 容量或投影预算导致未纳入的内容须记录明确诊断
- 从 frequency/necessity 切换到 all 时, 取消该路由已有自动参与计时任务并使旧补偿 ticket 失效; all 的普通提交不受 _submitted 中既有时间戳限制, 该时间戳本身不等同于冷却闸门

### 修改范围与验收

1. 更新平台策略唯一事实来源及前端派生契约, 添加 all 枚举
2. 更新唤醒决策, 输入可处理性检查与调度流程, 保留真实事件身份及过载诊断

5. 验收群覆盖和时段切换, 默认模式兼容, 全触发下不同成员工具权限仍按真实发言者检查

## 3. 已定位的问题

### P1. 元数据和冷配置重复解析

PluginCatalog.get 每次调用 scan, 查一个插件也读取全部插件
控制服务中调用 _edictum_config_service 或依赖它的插件管理服务的路由请求会重新创建 EdictumConfigManager, 构造时 reload 并归一化所有命名配置; 归一化每个插件规格再次执行 catalog.get, 并非每个 HTTP 请求都会构造此管理器
插件管理服务又另行扫描 Chat 状态和自身目录; 管理员快照在此基础上逐平台解析插件, 然后再次生成插件目录载荷
PluginCatalog 本身未缓存扫描或解析结果; plugin_authorization._factory_declarations 已有 (st_mtime_ns, st_size) 声明缓存, 因此不能描述为全仓完全没有元数据解析缓存

相关入口: satrap/edictum/plugin_catalog.py, satrap/edictum/config.py, satrap/core/config/plugin_service.py, satrap/core/backend/control_server.py

### P2. 控制服务事件循环存在同步阻塞

插件清单 GET 在异步路由中同步构造服务并扫描目录
全局配置 GET 虽把 get_config 放到工作线程, 服务构造在进入工作线程前已同步加载全部 Edictum 配置
多个页面请求共用控制服务事件循环, 因此 Promise.all 不能消除后端同步扫描带来的串行等待

### P3. 前端获取了当前界面不需要的数据

- 插件列表和插件详情分别重新获取全量目录, 没有共享已取得的目录快照
- EdictumPluginManager 打开时, 对所有具有参数 schema 的插件逐个请求全局配置, 无论当前是否选中
- Edictum 插件弹窗还无条件请求模型选项及知识库; 无相关字段时也需要这些接口完成
- GlobalPluginSettings 使用 Promise.all 等待配置, 模型选项和知识库全部完成后才展示参数
- Agent 页刷新会并行读取类型, 插件, 平台和全部命名配置, 每次保存后再次全量刷新

### P4. 插件修改后的应用范围过大

前端 Agent 页 EdictumSessionsPanel.savePlugins 保存命名配置后调用 applyRuntimeChanges, 进入 BackendManager.reload_config
该入口加载模型, 会话类和全部 Edictum 配置, 协调所有活跃 Edictum 会话, 再逐平台重载所有活跃会话的模型绑定
插件生命周期协调器已有差量判断, 未变化插件会跳过实际重装; 额外成本包括范围过大的配置准备, 逐会话扫描, 模型实例创建及等待会话操作锁

插件页的全局参数 PUT /config/plugins/{name}/config 和使用位置 PUT /config/plugins/{name}/usages 则通过 _apply_plugin_runtime 协调 Chat 与 Edictum 的全量实例, 不经过 reload_config
Chat 正式会话协调按顺序执行, 耗时随实例数量和生命周期回调增加
本轮未实际执行热应用, 因此具体某个插件的初始化, MCP 连接和清理回调耗时尚未实测

## 4. 性能修改批次与契约

### 第一批: 共享元数据快照与移除同步阻塞

- 同一次请求及一次热应用使用固定版本的目录快照, get(name) 从索引取值, 不重复完整解析
- 共享快照只读, 会话覆盖和前端序列化不能原地改写缓存条目; 需要可变数据时生成独立副本
- 按插件目录和 meta.yaml 的变化指纹刷新快照, 安装成功和显式刷新立即失效; 外部修改可被检测, 元数据错误继续记录
- 复用冷配置快照, 按实际文件修订重载, 单插件读取避免构造无关的全部管理服务
- 目录读取和配置准备进入有界工作线程; 并发构造同一快照合并为一次加载
- 缓存限制在元数据与带修订的配置读取; 不缓存调用者授权结果, 不延迟权限撤销, 不改变保存事务或审批前的实时复核
- 配置迁移保持幂等, 不为减少扫描跳过旧配置校验或改变工具启用状态

#### 缓存进程边界和并发加载

- 目录与冷配置快照各进程独立持有, 控制服务, 平台后端和 Chat 服务不共享 Python 对象或跨进程 Future; 相同文件的变动由各进程自己的指纹检查发现
- 目录缓存按规范化的内置/用户目录组合区分, 记录目录项集合及每个 meta.yaml 的文件指纹; 配置路径切换, 文件新增, 删除和原子替换均须失效, 不能只检查现有文件的 mtime
- 参考 _factory_declarations 的 mtime_ns/size 实现方式, 不复用其权限缓存对象; 指纹用于变更探测, 内容 revision 继续用于事务冲突判断, 两者不能互相替代
- 进程内 singleflight 表用 threading.Lock 保护, 键含资源标识与待加载指纹, 结果载体为 concurrent.futures.Future; 锁仅保护登记和发布, 不持锁读取文件, 不持锁 await
- 异步入口仅让领头请求向有界线程池提交一次加载, 其它请求通过 asyncio.wrap_future 等待并使用 shield 隔离单个请求取消; 等待者不占用工作线程, 不能在线程池中等待另一个仍排队于同池的任务
- 同步管理服务消费已加载的固定快照参数, 不在每个 get 中再次发起等待; 独立离线同步入口允许领头调用直接构造, 不依赖某个服务事件循环
- 载入期间指纹改变时, 旧任务不能覆盖新一代缓存; 完成前后核验指纹, 有界重读后仍变化则返回明确重试错误, 不把混合结果发布为最新快照
- 失败 Future 向本轮所有等待者传递相同异常并清除在途记录, 允许修复文件后再次加载; 单个等待者取消不取消仍被其它请求使用的加载
- 并发失效验收包括同指纹只加载一次, 旧任务迟到, 文件原子替换, 解析失败后恢复, 等待者取消及工作队列满, 不引入死锁

#### 配置版本探测接口

现有 config_document_revision 在读取完整文档后计算内容摘要, 插件参数 revision 也需要读取文件字节; 未发现独立的轻量配置版本路由
GET /config 只覆盖主文档且同时返回正文, 无法代表模型, 会话类, Edictum, Chat 插件开关及插件参数等独立配置文件的变化

第一批新增已认证的 GET /config/versions 作为变更探测入口, 与前端轮询拆分同批实施:

- 按 main_config, models, session_classes, edictum_configs, chat_plugins, plugin_catalog, plugin_defaults 等实际资源返回不透明 change_token 和可用状态, 允许请求指定资源; 存储路径与环境覆盖沿用现有解析规则
- 正常探测只读取配置来源和 stat/目录指纹, 不构造 EdictumConfigManager, 不解析全部插件 YAML, 不访问模型, MCP 或平台网络; 必要的主文档路径解析使用按指纹失效的冷快照
- change_token 仅表示客户端需要重读, 不作为 expected_revision 写入凭证或授权依据; 缺失, 损坏, 不可读分别报告, 不返回凭据或配置正文
- 详情读取与 change_token 必须对应同一代已核验来源, 读期间发生变化不能让客户端把旧详情记成新 token; 保存成功立即失效并返回或触发对应资源版本更新
- 仅有消费需求的页面探测对应资源, 文档隐藏时暂停, 普通健康检查不读取配置正文; 会话覆盖按选定范围单独探测, 不为了版本接口扫描所有历史会话
- 外部常规编辑和其它进程写入通过文件指纹被检测, 显式刷新强制重新核验内容; mtime/size 不变并不构成内容绝对未变的证明, 异常保留时间戳编辑需通过强制刷新或低频内容核验处理
- 管理员撤权及工具执行前的权限复核继续走现有实时路径, 不等待前端探测周期

### 第二批: 前端按需读取

- 插件列表和详情共享可失效的目录请求, 刷新和安装后主动失效
- 弹窗只读取当前选中插件的全局参数, 按插件名与修订缓存已完成结果; 合并同一请求, 防止切换时迟到响应覆盖新选择
- 仅在 schema 存在模型或知识库引用字段时读取对应选项, 参数先展示, 选项独立加载并显示错误
- 保存后只刷新受影响命名配置或插件, 保留草稿, 冲突比较和修订核验
- 管理员配置先展示已取得的内容, 运行状态独立确认; 未完成确认时不能显示 "已生效"

### 第三批: 定向运行应用

- 插件保存使用插件协调接口并传入命名配置或具体使用位置范围, 不调用通用 reload_config 重载无关模型
- 全局参数保存仅协调实际引用该插件且有效配置发生变化的实例, 同次应用复用目录和全局参数快照
- 未变化规格返回 unchanged; 模型实例仅在模型配置或有效绑定实际变化时重建
- Chat 协调使用有界并发, 每个会话仍使用原操作锁; 不为加速强制取消正在执行的模型请求
- 记录配置读取, 等待会话锁, 卸载, 安装和总应用耗时; 前端区分已保存, 等待应用, 应用成功和失败
- 超时不误报成功, 失败继续保留回滚和逐实例结果; 不引入绕过权限或生命周期清理的捷径

## 5. 验收标准

- 暖缓存同一次读取不重复解析未变化的 meta.yaml; 冷加载最多解析每个候选插件一次
- 元数据新增, 删除, 损坏和外部编辑能使快照正确更新, 内置插件优先级保持不变
- 并发慢读取不长期阻塞控制服务其它轻量接口; 保留工作队列满时的明确错误
- 只查看一个插件不请求所有插件全局参数; 不含模型或知识库字段的插件不等待相关选项接口
- 修改一个命名配置中的插件不重建无关会话的模型, 不重新安装未变化插件
- 权限撤销, 待审批操作复核, 配置冲突, 实例覆盖, 迁移和生命周期回滚原有测试继续通过
- 优化后按同一接口与配置规模复测, 记录 HTTP 读取耗时, 扫描次数及热应用分阶段耗时; 性能收益以实测为准

### 6.3. 新增问题与风险

#### P5. 全局轮询把配置当成运行状态反复读取

useBackendStatusSync 每 5 秒并行请求 health, status, 会话类和 Edictum 配置, WebSocket 已连接时也不减少读取
初始执行 refresh 后, WebSocket onConnect 还会执行 refresh; polling 仅合并本 hook 内尚未完成的一轮, 请求很快结束时仍可能紧接着出现另一轮
Dashboard, Platforms, Sessions 等页面会再次读取相同配置; useConfigStore 的代次检查仅防止旧响应覆盖新响应, 不合并请求

契约: 运行状态与配置刷新分离; 配置通过首次使用, 保存成功, 手动刷新和可核验的版本变化失效, 不跟随 5 秒健康检查反复全量读取
WebSocket 状态只覆盖 running 和 adapters 等部分字段, 必须保留其它状态字段的低频补查及断线回退, 不能简单删除全部 HTTP 状态读取
共享只读请求合并须按资源与范围区分, 外部配置编辑仍能被检测; 不缓存授权判断

#### P6. 启动被所有服务的认证串联到页面渲染前

main.tsx 先等待 loadRuntimeConfig, 再等待 establishApiSessions 完成, 最后才创建 React root
运行配置发现已有 2 秒 AbortController, 但认证 fetch 无显式超时; Promise.allSettled 仍要等待最慢的服务结束
认证已有按服务的 pendingSessions 请求合并, 不应把它误判为缺少认证请求去重

契约: 页面先显示启动状态或管理外壳; 按所用服务确认认证, 为认证增加明确截止时间和独立失败展示; 某服务异常不能阻塞其它可用页面
保留凭据保护, 401 单次重试和每服务请求合并; 未认证时不得发送受保护的业务请求或把失败显示为已连接

#### P7. 轮询控制不统一, 慢响应时可能叠加

- 插件使用位置 runtime 轮询已有 pending 防重入, 但未检查文档可见性
- 日志保留面板只检查 active 标签和保存状态, 没有文档隐藏检查或读取 pending 防重入
- 群详情, 群事件, 群动作和群同步轮询有可见性检查, 但未统一阻止上一轮读取未结束时再次发出请求; 响应代次保护不等同于网络防重入
- 群动作和手动唤醒部分状态已有轮询终止条件, 应保留

契约: 公共轮询机制支持 active, 文档可见性, 单次在途请求, 停止条件和失败退避; 恢复可见时合并补查一次, 不补发全部错过周期
配置草稿不被运行状态补查覆盖; 后端停止和历史账号范围不能继续调用依赖在线平台的接口

#### P8. 无关状态更新引发额外页面渲染

src 中有 17 处无 selector 的 useBackendStore() 或 useConfigStore() 订阅, 包括 Header, Dashboard, Settings 和 Agent 页
每次 loading, health 或不相关配置改变都可能触发整个订阅组件重渲染; 相同内容的配置响应也直接替换对象引用
当前 9 个插件的小列表场景未观测到因此产生的长任务, 此项是明确存在的无效工作与规模风险, 尚未单独量化其耗时占比

契约: 使用精确 selector, 对必要组合使用稳定比较; 未变化快照保留引用, 表单初始数据和选项分别管理, 保留脏状态与迟到响应保护
不以 JSON.stringify 全量大对象替代版本判断, 也不为减少渲染删除修订冲突校验

#### P9. 取消和截止时间在客户端之间不一致

ApiClient 默认 10 秒, controlClient 默认 30 秒, 全局插件保存和使用位置保存已单独配置 120 秒
Edictum 的通用 reload 和 reconcile/apply 仍走 ApiClient 默认 10 秒; 等待活跃会话锁或插件生命周期时可能前端先超时, 后端还在执行
Chat HTTP request 与认证 fetch 没有显式超时; 多数页面 cleanup 仅设置 disposed/live 或响应代次, 不取消只读请求
实际热应用未执行, 因此此处是代码确认的超时与操作结果风险, 不能声称本机已经发生某次 10 秒超时

契约: 区分短读取与长操作, 支持只读请求 AbortSignal 和截止时间; 页面切换只取消本页面已无人使用的读取, 不能中断其它消费者共享的请求
写操作超时显示结果待确认并允许查询实际状态, 不能当成后端已撤销或自动重试一次写操作; 长操作使用进度/状态查询或匹配服务端时限的显式超时

#### P10. 日志页高吞吐下存在实测主线程压力

每条日志都追加 React 状态, 对最多 5000 条数据过滤, 全量 map 为行节点, 并在 logs 变化后读取 scrollHeight 自动滚动
暂停只冻结展示快照, 接收缓冲和 React 状态仍继续更新; LogLineItem 的 memo 不能消除数组处理, 父组件遍历和新增节点成本

隔离生产构建中, 以 50 批各 100 条日志的突发夹具输入 5000 条日志, 两次记录:

- DOM 元素约 20171 个
- 各有 6-7 个超过 50 ms 的长任务, 总长任务时间约 484-504 ms
- 约 1.6 秒测量窗口中, renderer task 时间约 1.25-1.37 秒

这是高吞吐压力样本, 不代表用户平时的日志速率
契约: 有界缓冲批量提交, 可视区域渲染, 暂停时缓冲更新不反复重渲染冻结列表; 保留日志顺序, 筛选, 清空, 导出和 5000 条保留上限
自动滚动只在批次提交后且用户仍位于底部时执行, 不抢回用户阅读位置

### 6.5. 现有性能基准不能直接作为当前基线

benchmarks/fixtures.mjs 的 HTTP 夹具返回 Access-Control-Allow-Origin: *, 未提供允许携带凭据的 CORS 响应
当前 Axios 和 Chat fetch 均携带 credentials, 浏览器会拒绝该跨域响应; 实际使用原夹具打开 Chat, 记录 8 条 CORS 错误, "继续最近对话" 按钮没有出现
夹具的状态 WebSocket 消息还把 running/adapters 放在顶层, 与 SatrapWebSocket 要求的 data 信封不一致

契约: 修正夹具的 origin/credentials 和状态信封, 对未匹配接口, pageerror 和非预期 requestfailed 明确失败; 场景开始前核验数据已成功加载
修正前不引用旧 comparison.md 的数字说明当前优化收益; 本轮独立夹具使用正确 CORS 和 data 信封, 完成场景未出现 pageerror
