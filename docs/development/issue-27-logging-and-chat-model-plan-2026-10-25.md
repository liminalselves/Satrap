## 1. 目标与范围

本轮统一处理以下问题:

1. 区分会话限时, 模型网络超时和程序异常, 让超时原因在日志和用户反馈中可见
2. 日志监控不再依赖平台 Backend 启动, 可查看 Control, Backend 和 Chat 的独立日志
3. 日志文件按服务和日期合并, 不再按运行实例生成带 PID 和随机后缀的文件
4. Chat 提供整体默认模型, 每个会话保存自己的模型选择, 仅手动切换改变绑定
5. 普通发送与重试使用当前会话已确认的模型, 修复界面选择和实际调用不一致
6. 模型请求失败时提供简短错误码与原因, 并保留正确的失败状态

本轮不增加日志守护进程, 不引入消息队列或日志数据库, 不调整 SDK 自动重试策略, 不扩大现有 CI 的全量矩阵执行范围

## 3. 超时与错误的统一规则

### 3.1 保持两个超时设置的职责

- session_timeout: 平台单轮会话执行限时, 默认 120 秒, null 表示不限时; 保留现有模型, 工具和审批等待的计时边界
- network_timeout: 共用模型配置中的 SDK 网络超时, 默认 60 秒, Chat 和平台都使用
- 本轮不新增 llm_timeout, 不把网络超时误报为会话限时, 不声称 network_timeout 是完整流式生成的总时长
- Chat 当前没有接入平台 session_timeout, 本轮不把该设置静默扩展到 Chat
- SDK 可能自行重试, 最终失败的总耗时不保证等于一次 network_timeout

设置入口保留并明确说明:

| 设置 | 前端位置 | 生效范围 |
| --- | --- | --- |
| session_timeout | 管理面板 -> 系统设置 -> 会话限时 | 平台执行整轮会话; 留空保存为 null, 表示无限制 |
| network_timeout | 共用模型配置编辑弹窗 -> 网络超时 (秒) | 使用该模型配置的 Chat 与平台 SDK 网络等待; 默认 60 秒 |

界面提示和日志分别写明限时种类与配置值, 避免用户将网络等待限时理解为整轮生成限时

### 3.2 统一错误结构

同步, 异步, 流式和非流式共用最小错误信息:

| 字段 | 含义 |
| --- | --- |
| code | 项目内稳定错误码, 如 session_timeout, network_timeout, connection_error, authentication_error, rate_limit, provider_error, invalid_response |
| message | 可直接展示的简短原因, 不依赖可能为空的 str(exception) |
| status | 可取得时保存 HTTP 状态码, 不为连接失败伪造 HTTP 状态 |
| provider_code | 可取得且格式合法的供应商错误码 |
| request_id | 可取得的请求标识, 用于关联日志, 不以它代替原因 |

复用现有响应和 ModelCallError 通道传递信息, 流式 error 事件采用相同结构; 不增加另一套通用异常框架, 不用实例级 last_error 暂存并发请求的错误

### 3.3 日志与用户展示

- 会话限时, 最终网络超时使用 WARNING, 明确写出超时种类和配置值
- 连接失败与供应商拒绝记录分类, 模型配置名和可用的状态码; 未预期程序异常使用 ERROR 并保留必要异常链
- 正常取消独立处理, 不转换成网络超时或未知错误
- 一次最终失败产生一份主要诊断, 上层补充会话关联信息, 避免各层重复输出同一堆栈
- SDK 自动重试期间不提前声称请求最终失败, 不在本轮另加自动重试
- 用户显示示例: 请求失败 [HTTP 429 / rate_limit_exceeded]: 服务商限流, 请稍后重试
- 超时显示示例: 请求失败 [network_timeout]: 等待模型响应超时, 网络超时配置为 60 秒
- 只提取必要的供应商错误字段, 脱敏并限制长度; 不直接输出认证头, Key, 完整 URL 查询串, 请求正文或原始异常对象序列化结果

### 3.4 失败不能被当成正常回答

- 工作流显式处理流式 error, 把错误信息传至受控失败通道, 不再忽略后等待普通 done
- 非流式使用相同的失败信息, 不仅保留 模型调用失败 这一空泛说明
- Chat 广播可展示的错误, 并在当前回复版本保存失败状态和脱敏摘要, 刷新后仍可查看
- 错误说明不作为模型成功生成的 assistant 消息写入模型上下文
- 流中断时保留已展示的部分输出并标明未完成, 不冒充完整成功; 已确认发送的附件与工具副作用不被宣称已撤回
- 平台沿用当前错误反馈开关, 开启时发送简短错误说明, 关闭时仍记录诊断
- 排查 tools_agent 等同步/异步入口的固定失败文本, 确保已有结构化错误不会在上层重新丢失; 不把尚未复核的分支标为完成

## 4. 独立日志监控

### 4.1 使用已有内存流

- 保留每个进程的 standard_log_stream, 继续接收项目 logger 与已经接入的标准输出/错误流
- Control, Backend 和 Chat 分别提供 GET /api/logs, 返回相同格式
- 共用日志查询和响应构造代码, 各服务只完成路由与认证接线
- 不通过扫描磁盘来实现实时刷新, 不把文件日志级别提升到 DEBUG 来弥补实时接口缺失
- 保留 Backend 原有 /ws/logs 入口供既有调用方使用, 新日志页不再只依赖它

接口建议:

```text
GET /api/logs?limit=100
GET /api/logs?stream_id=<运行流标识>&after=<序号>&limit=200
```

响应包含 service, stream_id, entries, next_cursor, has_more 和 reset; 每项记录包含序号, 时间, PID, 级别和文本

### 4.2 增量与负载边界

- 每个运行流独立分配递增序号, 不依赖时间戳唯一性
- 复用现有 5000 条有界历史缓冲; 初次默认返回最近 100 条, 单次最多 500 条, 响应日志正文预算为 256 KiB
- 进程重启或游标已被淘汰时返回明确的 reset, 客户端重新取得有限快照
- 截断的展示条目显式标记, 不声称它是完整日志; 完整文件仍由文件日志策略决定是否保存
- 单条内存展示最多保留 16 KiB UTF-8 正文, 在字符边界截断; 5000 条缓冲与单次响应正文预算分别约束常驻量和返回量
- 前台默认每秒请求一次所选日志来源, 同一来源不并发轮询; has_more 时有限量追赶, 不形成无限忙循环
- 页面隐藏时暂停刷新, 返回页面后补取; 来源离线时退避并可手动重连
- 前端继续批量追加与虚拟列表展示, 不按单条日志更新整个页面
- 以 service, stream_id 和序号去重; 全部来源按时间展示, 同时保留各来源原有次序, 不承诺跨进程严格全序

### 4.3 页面行为与认证

- 来源选项: 全部, Control, 平台 Backend, Chat
- 每个来源独立显示连接, 离线和需要认证状态; Backend 停止不清空已看到的日志
- 日志页改为功能级认证, 不以任何单个服务 ready 作为整页准入条件; 每个来源按真实服务单独认证
- 一个服务不可用时保留其它来源的结果, 不用全页错误覆盖正常日志
- 来源重启或游标过期时提示已重新取得有限快照, 不假装期间的日志已完整补齐; 单个来源认证失败只触发该来源的恢复入口
- 保留级别筛选, 搜索, 暂停, 清空显示和导出; 导出注明来源
- 清空显示只影响前端缓冲, 不删除文件, 不撤销其它客户端的游标
- 新接口沿用现有访问密码与 Bearer 校验, 不因 Backend 未运行而开放匿名读取

## 5. 文件日志按服务与日期合并

### 5.1 命名与写入

新文件命名固定为:

```text
SATRAP-backend-20261025.log
SATRAP-control-20261025.log
SATRAP-chat-20261025.log
```

- 同服务同一天共用一个文件, 多进程记录允许混合
- 不按进程分组或重新排序, PID 仅作为排障资料; 不再以避免进程混写为理由创建文件后缀
- 重启后追加, 不覆盖已有内容, 不再因启动新进程创建另一个日志文件
- 日期沿用现有日志轮转使用的宿主本地日期; 跨日切换新文件
- PID 放进记录内容, 文件名不带 PID, 随机标识或启动时间; 保留现有 时间 -> 级别 的行首格式, 如 [2026-10-25 02:26:01.123] [WARNING]: [backend pid=28520] 网络请求超时, 避免破坏级别解析
- 内部活动登记可以继续复用已有运行标识和操作系统租约, 不把这些标识暴露为文件名后缀
- 显式 file_name 自定义路径继续保留既有语义, 不擅自改名

### 5.2 最小追加协调

- 复用 LogFileLock, 以服务为单位设置写锁, 不使用所有服务共用的管理锁串行化每条日志
- 一条格式化记录的追加与 flush 位于同一个短临界区, 允许不同进程的记录交错, 避免单条多行记录被合作写入者拆散
- 不要求跨进程按时间戳重新排序, 不引入中心写入进程或批量日志数据库
- 活动登记仅在文件切换等生命周期事件更新, 不在每条日志写入时重写状态文件
- 锁或磁盘失败沿用独立, 限频的诊断通道, 不递归调用相同文件 logger

这里的短写锁只保护一次完整记录的追加, 不隔离各进程日志; 不引入逐条全量权限复核或每条日志的活动登记写入

### 5.3 轮转, 清理与旧文件

- 活动文件由 多个运行实例 -> 同一文件 的关系保护, 不再要求文件名包含某个唯一运行标识
- 一个进程退出不表示共享文件无人使用, 清理检查全部活动使用者
- 轮转与清理保留现有维护协调, 不为简化文件名删除仍在使用的文件
- 保留天数和手动清理入口不变, 本轮不新增按大小拆分或日志压缩
- 清理器同时识别新服务日期格式, 旧 PID+随机后缀格式和更早的日期格式
- 新写入采用新格式, 旧历史文件不批量重命名, 拼接或搬迁; 它们按原保留策略自然退出

## 6. Chat 默认模型与会话绑定

### 6.1 选择规则

1. Chat 设置提供独立的 整体默认模型, 持久化到 .satrap/config/chat_settings.json, 复用已有配置文件读写机制
2. 没有该配置时沿用现有 default 名称, 不是自动选择列表第一项
3. 创建草稿/预加载会话时解析一次默认模型, 后续只有对该会话的手动切换才改变选择
4. 已有会话沿用 conversation_meta.model, 修改整体默认不重写已有会话或已有草稿的绑定
5. 刷新页面, 服务重启, 切换会话或更新模型列表时, 均从会话绑定回填选择
6. 模型被删除或不可用时显示明确状态并要求手动选择, 不静默切到另一个模型
7. 这里固定的是模型配置名, 同名配置的 Key, 网络超时和其它共享参数仍按当前共用配置更新; 不在会话里复制凭据或冻结整份配置

当前模型选择器只改变当前会话; 整体默认使用单独设置入口, 两者不隐式联动

预期页面行为:

- Chat 设置中显示 整体默认模型, 保存后提示仅影响之后创建的会话
- 输入框上方原有模型选择器显示当前会话的已确认绑定; 没有持久会话时显示当前草稿已选模型
- 新页面首次创建草稿读取整体默认一次; 已有草稿不随整体默认或模型列表刷新而改选
- 切换保存期间显示正在保存并禁用发送/重试, 成功后才更新已确认选择; 失败保留原选择并显示原因
- 切到另一会话回填该会话模型, 不沿用上一会话的下拉值; 已删除的绑定显示不可用并提供手动重选

### 6.2 接口与一致性

建议新增:

```text
GET /api/chat/settings
PUT /api/chat/settings
GET /api/chat/model?conversation=<ID>
PUT /api/chat/model?conversation=<ID>
```

- 全局设置保存复用配置版本校验; 会话模型复用现有元数据, 不另建模型绑定表
- 切换先校验配置存在并构造新客户端, 在既有会话操作锁内完成运行时切换与元数据保存
- 保存或应用失败时保留旧绑定并明确回执, 不出现界面显示成功但实际客户端未切换
- 保留现有上下文, 插件, 审批状态和项目绑定, 不靠删除并重建会话切换模型
- 生成或已有会话操作进行中时禁用切换, 后端也拒绝冲突请求, 不偷偷延迟成下轮切换
- 前端等待服务确认后更新已确认模型; 切换完成前不允许用新显示值发送或重试
- 切换会话时取消或忽略旧会话的迟到读取结果, 同一会话快速切换也按已接受操作处理
- 同名模型配置热更新继续沿用当前的生成中延后应用机制, 不改变模型选择
- 同一会话被另一个标签页修改后, 激活/重新读取时以服务端绑定回填; 发送和重试前若发现绑定不同于界面已确认值, 先同步并提示, 不悄悄用另一个模型执行

### 6.3 旧会话与 Fork

- 有元数据的旧会话直接沿用原 model, 不批量重写历史
- 无元数据的旧会话保持既有恢复规则, 后续显式切换后保存绑定
- Fork 继承源会话当前绑定, 之后两边的手动切换互不影响
- 整体默认只决定以后新建会话, 不改变已有 Fork 的绑定

## 7. 发送与重试的模型一致性

- 普通发送和重试均以服务端确认的当前会话模型为准
- 前端模型保存完成后再发请求, 不仅在 preload_settings 中带一个对持久会话不起作用的 model
- 请求受理时固定本轮模型, 本轮结束前不因全局默认或其它会话切换而改变
- 重试沿用原用户问题与附件, 保留旧回复版本, 使用当前会话模型生成新版本
- 重试不读取旧回复版本的模型来覆盖当前绑定, 不改写旧版本的模型标记
- 在回复版本元数据中记录本次实际使用的配置名与模型标识, 不保存凭据; 旧版本没有记录时显示未知, 不按当前模型补猜
- 从本轮实际客户端取得模型标识, 不在回复结束时读取可能已经更新的模型配置来回填; 成功和失败版本均保留已知的实际调用资料
- 新模型不支持原附件时, 在创建新回复版本和裁剪上下文之前报错, 保留原状态
- 手动切换和重试共享会话操作互斥, 拒绝冲突而不是让两个模型同时修改同一上下文
- 中断任务恢复继续遵守已有请求快照和指纹规则, 不把 普通重试使用当前模型 解释成强制换模型继续旧任务

| C | Chat 整体默认, 会话模型切换, 发送与重试一致性 | display/settings.py, display/service.py, display/server.py, display/recorder.py, Chat 页面, api/chat.ts, API 类型和相关配置文档 |

新增生产模块限于有明确职责的错误辅助, 日志 API 辅助和 Chat 设置读写; 实施时优先复用已有模块, 不把重复实现拆成新框架

每批补充已有业务测试模块并给出结果, 不默认新建大量单功能测试文件; 同步遵守 development-guidelines.md 的中文注释, 类型标注和失败处理规范

执行顺序: 先补齐 A 的遗留入口检查, 再完成 B 的文件与实时页面验收, 最后实施 C 的后端绑定和前端交互; 每批完成后再提交, 不把工作区初步实现算作已交付

## 9. 验收与性能检查

### A: 超时与错误

- 同步/异步, 流式/非流式覆盖 401, 429, 供应商 5xx, 网络超时, 连接失败和流中断
- 会话限时与网络超时使用不同错误码; session_timeout=null 时不产生会话到期事件, 主动取消不误报
- 错误码和简短原因在 Chat, 平台反馈与日志中一致, 刷新后失败版本仍保留摘要
- 请求正文和凭据不进入用户错误说明, 不把 SDK 错误当成正常成功回答

### B: 日志

- Backend 未启动时仍可查看 Control/Chat, 各服务认证和掉线相互独立
- 确认实时 INFO/DEBUG 能显示, 文件默认级别保持现状
- 同日同服务两个真实进程追加同一文件, 覆盖中文和多行记录, 记录完整且重启不覆盖
- 跨日切换, 一个使用者退出但另一个仍写入, 活跃文件清理保护, 旧文件保留期均有实际验证
- 进程重启, 游标落后, 大量日志, 页面隐藏恢复和断线重连不产生无界缓存或重复刷屏
- 实施前记录单来源读取与页面批量追加的基线, 实施后记录三来源下的延迟, 请求频率, 返回体积和缓冲上限
- 新增来源不靠重复扫描磁盘实现; 写入压测比较单进程与双进程共享文件吞吐和等待, 如成本过高先调整锁的持有方式, 不先堆积后台队列

性能结果按相同机器, 相同日志条数和相同中文/多行样本对照, 至少记录以下项目:

| 项目 | 修改前基线 | 修改后记录 |
| --- | --- | --- |
| 5000 条内存历史中读取最近 100 条 | Windows Python 3.13.5, 200 次, 平均 0.01466 ms, P95 0.01570 ms | 相同规模的增量快照与序列化耗时, 响应字节数 |
| 单进程写入 1000 条中文日志 | 0.00960 秒, 约 104163 条/秒 | 同样本追加耗时和吞吐, 写锁等待开销 |
| 双进程共享文件 | 待补旧实现对照, 不用单进程数据代替 | 总记录数, 完整性, 吞吐和等待 |
| 日志页面 | 待补浏览器基线, 不用内存函数耗时代替 | 三来源请求频率, 首屏日志出现耗时, 追加延迟, 返回体积, 缓冲峰值 |

以上已有数据是单次本地抽样, 不包含真实服务器网络和磁盘差异; 未测项目明确标记未验收, 不填写推算值

### C: 模型与重试

- 默认模型变更只影响以后新建会话; 会话 A/B, 多个标签页, 刷新, 重启和 Fork 保持各自绑定
- 实际捕获模型请求验证手动 A -> B 后普通发送与重试都用 B, 旧版本仍标记 A
- 切换失败, 模型删除, 附件能力不匹配, 连续切换和生成中切换均不造成界面与实际调用不一致
- 保留上下文和回复变体, 不重复追加用户消息, 不在失败时留下空的重试版本
- 验证同名共享模型配置更新与模型选择的区别, 不把参数热更新误判为会话换模型

在既有 logging, LLM protocol, workflow execution, display service, MiniHTTP, control dispatch 和前端场景模块内集中补充回归; 前端执行类型检查与构建, 浏览器仅补日志离线来源和模型切换/重试的端到端场景

Windows 本地验证之外, Linux 与 macOS 的文件追加和锁行为由现有 CI 矩阵复验; 没有实际执行的环境明确标记未验收

## 10. 提交与部署边界

- 实施仅修改代码与集中回归, 不改写用户现有配置和历史日志, 不自动重启运行服务
- 开工后按 A/B/C 形成可单独审查的提交, 每批附实际测试与性能结果
- 提交, 推送和部署状态分别记录, 不以本地测试通过代替远端验收
