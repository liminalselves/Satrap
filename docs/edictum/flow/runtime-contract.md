issue #4 已实现的行为约定 (P0–P3 完成于 issue-4 分支)。描述宿主执行流程时的行为, 插件作者写节点时可以依赖这些保证。节点怎么声明见 [node-contract.md](node-contract.md)。

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| 触发事件 | 一个触发磁贴发出的一次触发 (一条消息唤醒, 一个阈值批次, 一次交接工具调用), 或一个 WF 的完成事件。每个事件有唯一的 `event_id` |
| WF 运行 | 某个 WF 因一个触发事件而进行的一次运行, 有唯一的 `run_id` |
| 拉取 | WF 运行开始时, 宿主从它的数据口往上游求值数据节点, 遇到状态槽或另一个 WF 停止 |
| 等待者 | 正在等某次 transform 求值结果的 WF 运行 |

## 2. 条件求值: 三值语义

### 2.1 结果

条件节点和逻辑门的结果是三值之一:

| 结果 | 来源 |
| --- | --- |
| 真 | 函数返回 `True` |
| 假 | 函数返回 `False` |
| 错误 | 函数抛异常; 求值超时 (默认 150 毫秒); 条件线程池已满; `needs` 要求的上下文不存在; 读到的状态槽不可用 |

错误不能当成假处理。否则错误经过 NOT 会变成真, 把本该拦下的触发放过去。

### 2.2 逻辑门

| 门 | 规则 |
| --- | --- |
| NOT | 真→假, 假→真, 错误→错误 |
| AND | 有任一假→假; 否则有错误→错误; 否则→真 |
| OR | 有任一真→真; 否则有错误→错误; 否则→假 |

例子: `AND(假, 错误)` 为假, 因为不管错误那一项真实值是什么, 结果都是假。`AND(真, 错误)` 为错误。

触发经过 AND 门时 (一个触发加条件), 条件部分按上表计算:

- 真: 放行触发
- 假: 不放行, 写一条"被条件拦下"
- 错误: 不放行, 写一条诊断, 指出是哪个条件节点出错, 以及错误内容

两个触发经过 AND 门 (时间窗) 时, 触发本身没有三值, 只看是否在窗口内都到达。

### 2.3 磁贴和节点上的启用条件口

- 触发磁贴的 `when`: 多个条件按 AND 计算; 结果不是真就不发出触发
- transform 的 `when`: 结果为真时调用节点; 为假时按 `passthrough` 输出; 为错误时等待这个节点的 WF 运行全部失败, 不用 `passthrough` 代替。因为条件出错时宿主并不知道该不该过滤, 只能停止这次运行
- 平台回复的发送条件: 结果不是真就不发送, 为错误时写诊断

### 2.4 求值时机和次数

- 条件在触发经过时求值, 每个触发事件对每个条件节点最多求值一次, 结果在这个事件内复用
- 条件函数必须是同步函数, 不应做 IO
- 宿主不在事件循环线程里调用条件函数, 而是放进专用的有界线程池 `FLOW_CONDITION_WORKERS` (沿用 `satrap/core/utils/async_worker.py:18` 的 `BoundedAsyncWorker`, 首版 4 个线程, 运行加排队最多 32 个)
- 等待 150 毫秒没有结果就判为错误, 不再等函数返回; 函数在线程里继续跑完, 结果丢弃。实例引用在工作线程真正退出后恰好归还一次; 运行中的事件循环采用异步归还, 工作线程不得用 `run_coroutine_threadsafe(...).result()` 反向等待, 循环已停止或关闭时走有超时的线程内兜底
- 线程池已满 (提交时没有空位) 也直接判为错误, 并写诊断
- 这样第三方插件的条件函数即使阻塞, 也只会占住线程池, 不会卡住事件循环。线程池被卡满时, 所有条件都判为错误, 也就是都不触发, 流程停下但平台其他功能不受影响
- 内置条件节点 (消息条件, 时间段, 快照条件) 是宿主自己的代码, 直接在事件循环里求值, 不走线程池
- 条件函数拿到的配置和上下文都是只读的

## 3. transform 求值: 调度, 共享, 取消

### 3.1 共享边界

以触发事件为边界: 同一个触发事件驱动的多个 WF 运行, 拉取同一个 transform 节点时只求值一次, 共享结果。不同事件之间不共享, 每个事件各求值一次。

例: 一条 @ 消息同时唤醒 RP 和"记录员"两个 WF, 它们都拉取同一个关键词过滤节点, 过滤只执行一次。下一条消息再唤醒时, 重新执行。

不按"整个流程跑一次"来划分, 因为流程没有这个单位: 不同的 WF 由不同的触发分别唤起。

### 3.2 求值顺序

- 每个 WF 运行按拓扑顺序拉取它的上游
- 同一层里互不依赖的节点并发求值
- 同一次求值中, 一个节点的多个下游共享它的输出

### 3.3 等待者计数与取消

每次共享求值记录等待它的 WF 运行。

| 情况 | 处理 |
| --- | --- |
| 一个等待者被取消 (WF 被丢弃, 会话关闭, 运行超时) | 从等待者中移除; 计算继续 |
| 所有等待者都被取消 | 中断计算: 异步函数收到 `CancelledError`; 同步函数在工作线程里无法中断, 宿主丢弃它的结果 |
| 求值出错 (异常, 输出校验失败) | 所有等待者都收到同一个错误, 各自的 WF 运行失败 |
| 后加入的等待者 | 计算还在进行时可以加入; 计算已经完成时直接拿结果 |

### 3.4 超时

- 节点求值的超时取等待者里剩余时间最长的那个 WF 运行的超时; 没有任何等待者设置超时时, 用宿主默认值 (首版 60 秒)
- 超时算求值出错, 按上表处理

### 3.5 失败的后果

只要一个 WF 运行因为上游求值失败而失败, 都按 WF 失败处理:

- 驱动它的阈值磁贴, 这个 WF 的已提交位置不推进; 同一批次驱动的其他 WF 各自推进, 互不影响 (见第 3.6 节)
- 它要写的状态槽不提交
- 不发出完成事件
- 按第 10.1 节记录和告知

### 3.6 阈值批次: 每个 WF 各自的已提交位置

一个阈值磁贴可以驱动多个 WF。磁贴为它驱动的每个 WF 各存一个**已提交位置** (桶内消息序号):

```text
磁贴 th:
  agent:    已提交到 #120
  recorder: 已提交到 #96     ← 上次这一批失败了
```

规则:

- 判断阈值时, 对每个 WF 分别看"它的已提交位置之后"的新消息
- 满足阈值时, 只触发那些满足的 WF, 每个 WF 拿到的批次是"它自己的已提交位置之后"的消息 (受 `max_batch` 限制)
- WF 运行成功, 并且它要写的状态槽都提交成功后, 才把这个 WF 的已提交位置推进到批次末尾。状态槽提交和位置推进在同一个事务里完成
- WF 失败: 它的位置不动, 下次满足阈值时只重试它; 其他已成功的 WF 不会因此重跑
- 磁贴的展示游标 (编辑器和运行状态接口里显示的) 取各 WF 已提交位置的最小值, 只用于展示和判断积压
- 磁贴新增驱动的 WF (用户改了流程) 从当前桶末尾开始, 不回放历史; 去掉的 WF 删除它的位置记录

执行语义:

| 范围 | 保证 |
| --- | --- |
| 同一个 WF 对同一批消息 | 成功之前可能运行多次; 成功之后不会再运行 |
| 状态槽 | 只在 WF 成功时提交, 不会因为重试多出版本 |
| WF 内部的工具副作用 | 至少执行一次: WF 运行到一半时工具已经执行, 之后才失败, 重试时工具会再执行一次。流程层不做去重, 由工具自己的恢复策略负责 (现有机制: 工具的 `recovery_policy`, 例如 `group_chat_reply` 为 `manual`, `satrap/expend/plugins/group_chat/tools.py:557`) |

## 4. 端口输入输出

### 4.1 输入

| 情况 | 函数收到 |
| --- | --- |
| 必填输入, 已连线 | 上游的值 |
| 可选输入, 没连线 | `None` |
| 可选输入, 已连线但上游输出空值 | 该类型的空值 (`()`, `""`, 版本 0 的空 `StateView`), 不是 `None` |
| `multiple` 输入 (首版插件节点不支持声明) | 按连线在存档 `edges` 里的顺序组成 tuple |

`None` 和空值要区分开: 没连线表示"这个流程不用这项输入", 空值表示"连了线, 但这次没有数据"。

### 4.2 不可变

- `messages` 和 `context` 以 tuple 传入, 元素是 frozen dataclass
- `StateView` 是 frozen 的
- `ctx.config` 是只读映射
- 这样多个等待者和多个下游共享同一份结果时, 不会互相影响。节点要修改数据时, 生成新对象 (例如 `FlowMessage.with_text()`)

### 4.3 输出

| 情况 | 处理 |
| --- | --- |
| 单输出节点返回值 | 当作那一个输出 |
| 多输出节点返回 dict | 键必须和 `out` 声明完全一致, 多了或少了都算出错 |
| 返回 list | 宿主转成 tuple |
| 类型不对 (比如 `messages` 输出里混入字符串) | 算求值出错 |
| 返回 `None` | 算求值出错; 想输出空值时要显式返回空值 |

## 5. 模型调用预算与计量

### 5.1 计数器

宿主按流程会话维护调用记录 (`FlowCallBudget`, `satrap/edictum/flow/budget.py`), 每次模型调用记一条:

| 字段 | 内容 |
| --- | --- |
| `source` | `wf` (WF 节点的模型调用) 或 `plugin` (插件节点的模型调用) |
| `node_id` | 发起调用的节点 |
| `event_id` | 所属触发事件 |
| `run_id` | 仅 `source: wf` 时有值: 所属 WF 运行。插件节点的调用可能被多个 WF 运行共享 (第 3.1 节), 不属于任何一个运行, 这里留空 |
| `time` | 调用开始时间 |

计量范围:

- 宿主只能统计经过它的调用: WF 节点的模型调用, 以及插件节点通过 `ctx.resources` 拿到的模型客户端 (宿主包装后自动计数, 插件不用自己上报)
- 插件自己直接请求外部 API (自己建 HTTP 客户端) 宿主统计不到, 不在预算保证范围内; 插件契约要求模型调用都通过 `ctx.resources`, 但宿主无法强制

### 5.2 软限制: 条件节点

`llm_budget.within` 这类条件节点只读计数, 在触发前判断要不要开始。`scope: target` 且未显式填写 `target` 时, 目标是本次事件经触发图可达的 WF 集合; 只有一个候选时统计该 WF, 多个候选时取各 WF 已用量的最大值, 因而阈值条件采用最严格结果。它不保证上限:

- 一次运行可能有多轮模型调用
- 两个触发同时通过时, 都会开始运行

适合"忙的时候少回几句"这类不要求精确的场景。

### 5.3 硬限制: 宿主预算

需要保证上限时用硬限制, 不是节点, 写在配置里:

| 配置 | 位置 | 含义 |
| --- | --- | --- |
| `budget.max_calls` + `window_minutes` + `count` | `params.flow.budget` | 整个流程在窗口内的模型调用上限; 共享的插件节点调用只计一次 |
| `max_calls_per_run` | WF 节点配置 | 单次运行中这个 WF **自己发起**的模型调用上限, 和 `max_steps` 并列; 不含它拉取的插件节点的调用 |

执行方式:

1. 每次模型调用前 (WF 的每一轮, 插件节点的每次调用), 宿主在同一把锁内检查并扣减计数
2. 超出任一限制: 这次调用不发出, 抛 `BudgetExceeded`
3. 在 WF 里: 本次运行失败, 走第 3.5 节的失败后果
4. 在插件节点里: 节点求值出错, 等待者全部失败
5. 调用发出后失败 (网络错误等): 计数不退回, 因为请求可能已经被模型服务计费

`count: all` 时插件节点的调用也计入, 这是默认值。`count: wf` 只算 WF 的调用。

### 5.4 计数存储

首版只存在内存里, 按窗口滚动。重启后计数清零。要不要持久化, 等实际使用后再定。

## 6. 状态槽

### 6.1 写入方

- 每个状态槽只能有一个写入方 WF, 编辑时检查 (`flow_state_multi_writer`)
- 同一个 WF 同一时间只有一次运行 (`on_busy` 决定再次触发时排队, 合并还是丢弃), 所以正常情况下不会并发写同一个槽

### 6.2 版本检查 (CAS)

仍然可能出现并发提交的情况: 用户改了流程 (换了写入方, 旧运行还没结束), 或两份流程配置绑到同一个群并写同名状态槽。所以提交时做版本检查:

1. WF 运行开始时记下它读到的状态槽版本 `base_version` (开启"写入方读取上一版"时就是传给它的那一版; 没开启时也记录)
2. 提交时在同一个事务里检查: 当前版本 == `base_version` 才写入 `base_version + 1`
3. 不相等: 拒绝提交, 本次 WF 运行算失败 (阈值位置不推进, 不发完成事件), 写诊断 `flow_state_conflict` (记录 `base_version` 和当前版本), 按第 10.1 节告知
4. 同一个 WF 写多个状态槽时, 全部检查通过才一起提交, 任一冲突全部不提交

### 6.3 提交内容

| 字段 | 内容 |
| --- | --- |
| `content` | WF 通过 `snapshot_write` 写入的内容; 超过 `max_chars` 时拒绝写入, 工具返回错误给模型 |
| `version` | `base_version + 1` |
| `covers_to` | 由阈值批次触发时为批次末尾的消息序号; 其他触发保持上一版的值 |
| `committed_at` | 提交时间 |
| `run_id` | 写入它的 WF 运行 |

WF 运行中可以多次调用 `snapshot_write`, 只有最后一次的内容在 WF 成功结束时提交; WF 失败时全部丢弃。

## 7. 配置合并与迁移

### 7.1 合并顺序

```text
类型默认 (config_schema.default)
  < 插件全局默认 (<插件名>.flow_nodes.json)
  < 流程默认 (params.flow.defaults)
  < 本节点 (nodes[].config)
```

- 某层没有这个键表示继承上一层
- 某层写了 `null`: 字段 `nullable: true` 时表示明确为空, 否则校验报错
- 对象和数组整体替换, 不深合并
- 首版不支持单个群覆盖流程节点的字段

### 7.2 版本

三处配置都记录自己按哪个节点契约版本写成:

| 位置 | 版本字段 |
| --- | --- |
| 本节点 | `nodes[].version` |
| 流程默认 | `params.flow.defaults[类型].version` |
| 插件全局默认 | `<插件名>.flow_nodes.json` 的 `nodes[节点名].version` |

版本缺失时按 1 处理。

### 7.3 迁移流程

读取流程配置时, 对每一处配置分别执行:

```text
for v in (记录的版本 + 1) .. 当前版本:
    按 renamed[v].fields 改键名
    调用 migrate(节点名, v, config)   # 有这个函数时
用当前 config_schema 校验一次
```

连线按所连节点实例的版本, 逐版本应用 `renamed[v].ports`。

规则:

- 先完成所有版本的迁移, 再校验一次; 中间结果不校验
- 四处迁移互相独立: 流程默认迁移失败不影响节点实例的迁移, 但流程整体判为不可运行
- 失败 (`migrate` 抛异常, 或最终校验不过) 报 `flow_node_config_stale`, 指出是哪一处, 流程不可运行; 原始配置不改动
- 迁移结果什么时候写回:
  - 节点实例, 流程默认, 连线: 用户下次保存流程时
  - 插件全局默认: 插件升级后宿主首次加载时, 原子写回一次, 写前备份原文件
- 记录的版本高于当前版本 (插件降级): 不迁移, 报 `flow_node_version_ahead`, 流程不可运行

### 7.4 生效配置的计算时机

- 会话创建时计算每个节点的生效配置
- 每条消息只先比较插件目录、节点声明、实现文件和全局默认文件的 `mtime+size`; 没有变化时不重新解析节点、不运行静态分析、不读取或哈希插件默认内容, 也不重建实例。文件保存接口的并发冲突检查仍使用内容 SHA256 修订号
- 任一层变化 (节点配置保存, 流程默认保存, 插件全局默认保存, 插件升级) 时重新计算, 只有生效配置真的变化了的节点才重建实例 (见第 8 节)

## 8. 节点实例生命周期

| 时机 | 函数写法 | 类写法 |
| --- | --- | --- |
| 会话创建 | 无 | 每个节点 id 建一个实例, 调用 `setup(ctx)` |
| 生效配置变化 | 下一次调用直接用新配置 | 新建实例并 `setup`; 进行中的求值用旧实例完成后, 调用旧实例的 `close()` |
| 插件重装 (版本或代码变化) | 重新加载模块 | 同上, 用新代码新建实例 |
| 会话释放 | 无 | 调用 `close()` |

- `setup` 失败: 节点不可用, 拉取它的 WF 运行失败, 诊断里写明; 宿主不自动重试, 下次配置变化或会话重建时再试
- `close` 失败只写日志, 不影响其他节点
- 实例不应该跨运行保存业务状态; 跨运行的数据放状态槽, 或插件自己的存储

## 9. 编辑时检查与运行时授权的边界

| | 编辑时检查 | 运行时 |
| --- | --- | --- |
| 依据 | 节点契约, `flow.workflow` 声明, 当前插件目录 | 现有权限, 插件执行开关, 能力启停状态, 模型配置是否存在 |
| 目的 | 提前告诉用户流程会不会出问题 | 实际决定能不能执行 |
| 不一致时 | 只是提示 | 以运行时为准 |

例:

- `group_chat` 声明 `foreground_only`, 编辑时检查据此报"装在后台 WF 上"。但运行时能不能发送, 仍由现有的发送权限和审批决定
- 插件节点所属插件在运行时被管理员关闭执行开关, 编辑时检查可能还没发现, 运行时拉取到这个节点就失败, 报 `flow_node_plugin_disabled`
- `provides` 只用于静态检查, 不授予任何权限
- 平台回复节点的 `flow_reply` 发送走现有发送权限和审批; 后台发送 (无来源消息) 还要求适配器支持主动发送, 不支持时这次发送失败, 按第 10.1 节处理

## 10. 重启与持久化

| 状态 | 重启后 |
| --- | --- |
| 阈值磁贴每个 WF 的已提交位置 | 保留 (持久化) |
| 状态槽的内容, 版本, 覆盖位置 | 保留 (持久化; 与已提交位置在同一个库, 同一事务写入) |
| 正在进行的 WF 运行 | 丢弃; 阈值批次因为这个 WF 的位置没推进, 会重新触发 |
| 排队中的触发 (`on_busy: queue`) | 丢弃 |
| 合并待重跑 (`on_busy: merge`) | 丢弃; 阈值类的会因位置没推进而重新触发 |
| AND 门时间窗内已到达的触发 | 丢弃 |
| 群唤醒的计数和冷却 | 丢弃, 从零开始 |
| 模型调用计数 | 丢弃 (第 5.4 节) |
| 节点实例 | 重新创建, 调用 `setup` |

`/new` 不是重启: 每个 WF 的对话历史清空, 档案起点 (`history_started_at`) 更新; 状态槽和阈值位置按各自的 `on_new` 配置处理 (状态槽 `keep` / `clear`, 默认 `keep`; 阈值磁贴 `drop` / `drain`, 默认 `drop`)。`drain` 在新会话接管时先按已提交位置把每个落后 WF 的积压批次跑完 (受 `max_batch` 限制, 等待上限 120 秒, 超时或位置不推进的按 `drop` 结算并写诊断), 因为档案起点更新后起点之前的消息对桶和阈值不可见。消息 `observe` 只暂存新事件并启动独立结算任务, 不内联等待这 120 秒; 调度器串行观察队列和会话内暂存均最多 256 条, 溢出时最旧事件按 `drop` 结算、清理临时文件并写 `flow_new.queue_drop`; 结算成功后按到达顺序回放, 单条回放异常时保留该事件供下次重试。`drain` 仍经引擎的 busy/queue/merge/drop 调度, 不直接并发运行 WF; drain 超时先取消并收殓旧 WF 及其排队事件, 再推进 drop 位置, 旧任务不得晚提交或晚发送。

### 10.1 WF 运行失败的处理

宿主不做退避, 也不暂停磁贴。阈值批次失败后这个 WF 的已提交位置不推进, 下次满足阈值时照常重新触发 (只重试失败的 WF, 见第 3.6 节)。失败时只做三件事:

**1. debug logger 记录**

通过现有诊断接口 `record_debug` (`satrap/core/log/debug/hooks.py`) 写入, 在 `/debug on` 的群里可以看到。流程新增的诊断类别:

| 类别 | 阶段 | 内容 |
| --- | --- | --- |
| `flow_trigger` | `fire` / `blocked` | 哪个磁贴发出触发, 或被哪个条件拦下 (含三值结果); 摘要带 `flow_name` 和 `scope_key`, 运行状态接口从持久化诊断库读最近 50 条 |
| `flow_run` | `start` / `end` | WF 运行的 `run_id`, `event_id`, 触发来源, 结束状态 |
| `flow_node` | `start` / `end` | transform 或条件节点的节点类型、事件与运行身份; 结束记录求值耗时、true/false/error 结果、完成或失败状态及错误类型; 条件 false 与 error 在触发摘要中也分别标记 |
| `flow_state` | `commit` | 状态槽提交的版本和覆盖位置 |
| `flow_budget` | `exceeded` | 硬限制拦下的模型调用 |

WF 内部的模型调用和工具调用沿用现有的 `execution_run` 等类别 (`satrap/core/framework/Base/execution/store.py:168-224`), 不另起一套。

**2. 普通日志**

不管有没有开 debug, 都用 `logger.error` 写一行, 包含群, 流程配置名, 节点 id, `run_id` 和错误摘要。

**3. 在群里发一条告知**

- 发送用途为 `error_feedback`, 和现有调度器的出错反馈一致 (`satrap/core/pipeline/scheduler.py:1148`): 不算业务送达, 发送失败只记日志
- 前台 WF (有来源消息) 回复到那条消息; 后台 WF (阈值, 交接, 完成触发) 没有来源消息, 走后台发送通道
- 内容只说明哪个 WF 失败和简短原因, 例如"Agent 本次更新失败: 模型请求超时", 不带堆栈或配置
- 同一个 WF 连续失败只告知一次; 成功运行一次后, 下次失败再告知。否则模型服务出故障时每条消息都会触发一次告知
- 跟随调度器现有的 `error_feedback` 开关: 关闭时不发告知, 前两项照常记录

## 11. 消息观察、唤醒与发送

- 入站消息仍由平台先入档再交给调度器; 已确认的出站回显和主动发送快照先 `await` 真实档案提交 (SQLite 经 `asyncio.to_thread`), 提交成功且为新记录后才异步通知 flow 观察者。通知队列满不会丢非 flow 档案, 发送返回时无需 drain 即可按消息 id 读取、去重和恢复
- flow 消息在稳定路由锁内只复核映射并投递到会话自有的串行观察任务, 锁内不执行初始化、阈值检查或 WF; 映射代际复核与消息顺序保持有效
- source 直连 WF 或自定义 transform 时保留完整档案视图; 仅 source→bucket→assemble (或 source 直连 assemble) 按下游需要查询: 最新 `max_pending` 条未覆盖消息与 `latest_n`, 在同一事务内按 seq 去重, 不翻页读取整个保留期
- 运行状态异步读取 SQLite; 诊断关闭、诊断库无该流程事件或读取失败时回落进程内摘要, `events_source=memory_fallback`, 有持久化事件时才是 `debug_store`
- 同一适配器可承载多个流程会话; 出站观察按冻结 `MessageScope.key` 精确分发, 不修改其他会话的绑定, 会话关闭时注销观察者
- `wake.use_platform_policy: true` 时使用平台唤醒判定; 私聊视为始终满足唤醒
- `wake.use_platform_policy: false` 时只使用流程自己的 `@`、唤醒词、`new_messages` 和冷却规则, 不继承平台判定; 任一自定义规则命中都可触发, 命中后 `new_messages` 计数清零
- `@` 只根据平台事件的结构化提及组件和归档的 `mentions` 判断, 不扫描文本里是否出现 `@`; 私聊消息的 `mentions_bot` 恒为真
- WF 的 `timeout_seconds` 包含输入拉取和模型工具循环, 默认 60 秒; transform 的每个等待者只等待自己的剩余时间
- 前台 `flow_reply` 在来源消息的 `ReplyTurn` 作用域内发送; 阈值等无来源消息的运行经 `ScheduledTarget` 与 `FlowSendRecorder` 走后台发送, 并保留每段回执证据
